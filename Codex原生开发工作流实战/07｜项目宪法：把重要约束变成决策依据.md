# 07｜项目宪法：把重要约束变成决策依据

上一讲的 `AGENTS.md` 像一张入职卡：告诉 Codex 从哪里进入、怎样工作、如何验证。但当它遇到两种都“能跑”的设计时，还需要更深一层的判断依据。

例如 PocketTasks 要增加云同步。方案 A 让界面在请求成功后直接更新内存；方案 B 先把服务端结果写入 Room，再让 UI 继续观察本地数据。两者都能展示最新任务，但只有一个符合“本地数据库是离线场景事实源”的长期设计。

项目宪法就是用来保存这种不应随单次任务摇摆的原则。

## 宪法与说明书有什么区别

README 回答“项目是什么、怎样运行”；AGENTS.md 回答“协作者怎样进入和工作”；Spec 回答“这次功能怎样表现”；constitution.md 回答“当存在多种选择时，我们依据什么取舍”。

宪法不需要很长。它应该只容纳那些满足三个条件的原则：跨越多个功能、违反后果明显、团队愿意在评审中真正执行。

## PocketTasks 的六条原则

### 原则一：离线核心能力优先

创建、查看、编辑和完成任务不依赖网络。引入网络数据源时，本地持久化仍然是上层读取的事实源。

这条原则会影响 Repository 设计、同步队列、冲突处理和测试策略。

### 原则二：状态单向流动

界面渲染不可变 UI State，用户操作以事件向下传递，数据变化从事实源重新流回界面。不要在多个层次维护同一份可变任务列表。

### 原则三：数据安全高于迁移便利

已经发布的 Room Schema 发生变化时，必须有显式 Migration 和升级测试。不能为了让开发构建“先跑起来”而启用破坏性迁移。

### 原则四：复杂度必须有需求理由

UI 层和数据层是基本边界；领域层只有在逻辑跨 ViewModel 复用或显著降低复杂度时才引入。一个只转发 Repository 调用的 Use Case 不是天然进步。

### 原则五：可观察行为必须可验证

每条验收标准要对应自动化测试或明确人工步骤。没有设备时可以不跑仪器测试，但必须如实报告。

### 原则六：用户信任不可透支

权限、通知、后台执行、遥测与外部服务连接都采用最小必要原则。敏感数据不进入日志、提示词、示例文件和公开 CI 输出。

## 把原则写成有牙齿的条款

一句“关注数据安全”太抽象。每条原则最好包含四部分：

```markdown
## III. 数据迁移必须可恢复

规则：已发布数据库版本的结构变化必须提供显式 Migration。
理由：任务是用户创建的数据，开发便利不能以静默丢失为代价。
执行：提交包含导出 Schema、Migration 和升级路径测试。
例外：仅限尚未发布、没有真实用户数据的原型；须在 Plan 中记录。
```

规则告诉 Codex 做什么，理由帮助它处理未列举场景，执行条款提供评审抓手，例外机制防止原则变成僵化口号。

## 冲突时怎样裁决

假设产品希望“任务完成后立即从进行中列表消失”，设计担心突然消失让用户困惑。宪法不会替团队做产品决定，但会给出裁决顺序：

1. 先满足已确认的用户行为和数据安全；
2. 再保持状态单向流动与单一事实源；
3. 在不破坏前两项的前提下优化交互；
4. 若必须偏离原则，在 Plan 中记录理由、影响和回收条件。

这使例外成为一个可见决定，而不是藏在实现里的偶然。

## 让 Codex 真正使用宪法

仅仅创建文件还不够。需要在根 `AGENTS.md` 中加入入口：

```markdown
## 决策依据

开始跨层功能、数据模型、权限或后台任务前，先阅读 docs/constitution.md。
方案与宪法冲突时，不要自行绕过；在 Plan 中指出冲突并请求决定。
```

在 Plan 模板中也加入一栏：

```markdown
## 宪法检查

- 涉及的原则：
- 是否存在偏离：
- 偏离理由与回收计划：
```

这样，原则会在做决定的时刻出现，而不是只在培训时被阅读。

## 宪法也要演进

原则不是永远不变，但修改成本应高于普通文档。每次修订写清日期、动机、受影响的工程规则与迁移动作。如果团队决定从纯本地应用演进为多端同步产品，“本地数据库是唯一事实源”可能需要重新表述；这应是一项正式架构决定，而不是某个功能顺手改掉。

## 本讲实践

从最近三次 Android 代码评审中寻找重复意见，把它们分类：

- 只适用于某个任务：放回 Spec 或 Review；
- 每次工作都要执行：进入 AGENTS.md；
- 体现长期技术价值并影响取舍：候选宪法条款；
- 可以自动判定：优先交给 Lint、测试、Rules 或 Hooks。

最后只选择 5 到 8 条真正愿意执行的宪法原则。少而有力，胜过面面俱到。

## 小结

项目宪法不是装饰性的价值观，而是设计冲突出现时的裁决依据。它用理由与执行条款连接业务目标、架构选择和评审动作。

到这里，我们已经有了项目记忆和决策原则。下一讲要解决另一个效率问题：怎样把反复输入的“生成 Spec”“审查 Android 改动”变成团队成员都能找到、都能正确调用的任务入口。
