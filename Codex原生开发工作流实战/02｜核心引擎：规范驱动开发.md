# 02｜核心引擎：规范驱动开发

上一讲我们把开发者的新职责概括为“定义正确”。可真实需求偏偏很少是清楚的。产品说“给待办增加筛选，离线也要可用”，这里至少藏着五个问题：筛选条件有哪些？它是否需要跨进程保存？空状态怎样显示？完成任务后是否立即消失？“离线可用”是否意味着未来还要同步？

如果这些问题没有被回答，Codex 只能用自己的常识补齐空白。它越能自主执行，偏航的距离就可能越远。

规范驱动开发（Specification-Driven Development，SDD）要做的，就是在编码之前建立一份可讨论、可执行、可验证的共同语言。

## Spec 不是更长的需求文档

传统需求文档经常描述“要有什么页面和按钮”，却没有把行为边界说清。一个可执行 Spec 更像测试与设计之间的合同。

比较下面两句话：

```text
模糊：增加友好的任务筛选功能。

可验证：任务列表提供“全部 / 进行中 / 已完成”三个筛选项；
切换筛选不修改任务数据；完成当前可见任务后，列表立即按当前筛选更新；
进程重建后仍恢复最近一次筛选；没有匹配项时显示与“尚未创建任务”不同的空状态。
```

第二段不一定完美，但开发、测试和产品可以围绕同一句话讨论。它也让 Codex 知道要追踪 UI State、持久化偏好与 Room 数据流，而不是只添加三个按钮。

## 一条可靠的“编译链”

在本课程里，需求会经过四次逐步降维：

```text
意图：为什么做、给谁解决什么问题
  ↓
Spec：系统必须表现出什么可观察行为
  ↓
Plan：哪些组件改变、为何这样设计、风险在哪里
  ↓
Tasks：按依赖排序的最小可验证动作
  ↓
代码与测试：实现行为并给出证据
```

为什么不从 Spec 直接跳到代码？因为 Android 的架构选择需要显式推理。例如“保存筛选条件”可以用 `rememberSaveable`、`SavedStateHandle` 或 DataStore。它们解决的是不同生命周期的问题。Plan 必须先说明要跨越哪一种边界，再决定技术。

## Spec 的五块骨架

一份实用的 Spec 不需要写成论文，但最好回答五类问题。

### 1. 背景与目标

谁遇到了什么问题？成功后发生什么变化？例如：“用户完成多项任务后，列表变得嘈杂；需要在不改变任务数据的前提下快速聚焦未完成事项。”

### 2. 范围与非目标

明确这次做什么，也明确不做什么。PocketTasks 第一版筛选只处理本地任务，不引入账户、云同步和跨设备筛选同步。非目标可以阻止 Codex 热心地扩张范围。

### 3. 用户场景

用具体路径描述行为：应用首次打开、已有数据、切换筛选、完成任务、进程重建、数据库读取失败。场景比组件清单更接近用户看到的结果。

### 4. 验收标准

每一条都应当可以通过测试、截图、日志或人工步骤验证。避免“流畅”“合理”“优雅”这类没有尺度的词；如果必须使用，就补充可观察定义。

### 5. 未决问题

不确定性不该被藏起来。把“筛选是否跨冷启动保存”列为问题，比 Codex 默默选择一种答案更安全。

## 从验收标准推导测试

下面看一条小型映射：

| 验收行为 | 最合适的证据 |
|---|---|
| 选择“已完成”只显示完成项 | ViewModel / Use Case 单元测试 |
| 点击筛选后标签状态改变 | Compose UI 测试 |
| 完成任务后 Room 数据仍保留 | DAO 或 Repository 测试 |
| 重建 Activity 后筛选仍存在 | 仪器测试或明确的手工验证 |
| 工程没有引入新的 Lint 问题 | `./gradlew lintDebug` |

这张表体现了一个重要原则：先确定要证明什么，再选择测试层级。不要让 Codex 为了“覆盖率好看”给每一层复制同一种测试。

## Tasks 不是把 Plan 切成句子

好的任务项应该能够独立完成、独立验证，并写清依赖。比如：

```markdown
- [ ] T003 定义 TaskFilter 及其过滤规则
  - 文件：app/src/main/java/.../model/TaskFilter.kt
  - 测试：app/src/test/java/.../TaskFilterTest.kt
  - 依赖：无
  - 验证：./gradlew :app:testDebugUnitTest --tests '*TaskFilterTest'

- [ ] T004 将筛选状态接入 TaskViewModel
  - 依赖：T003
  - 验证：ViewModel 测试覆盖切换筛选与任务完成后的列表变化
```

这类任务给 Codex 清晰的停止点，也给评审者一条能够复现的证据链。

## 什么时候不必完整走一遍 SDD

不是每次改动都值得写三份文档。修正文案、更新注释或调整一个已知样式，可以直接描述目标和验证方法。是否升级流程，取决于风险，而不是代码行数。

当改动涉及以下任一情况时，完整 Spec 和 Plan 通常很划算：数据模型或 Room 迁移、用户数据可能丢失、权限或隐私、跨模块接口、并发与后台任务、发布配置、需求存在多种合理解释。

## 小结

规范驱动开发把模糊意图逐步“编译”为可以执行和验证的工作。Spec 约束行为，Plan 解释结构，Tasks 管理步长，测试与命令提供证据。

有了发动机，我们还需要看清整辆车。下一讲会建立 Codex 的系统地图：CLI、IDE、桌面应用和 Cloud 各自适合什么，又如何共享同一套项目规则。
