# PocketTasks 项目宪法

版本：1.0  
生效日期：2026-08-06

本文件用于裁决跨功能的架构与质量取舍。普通实现细节不应进入这里。

## I. 离线核心能力优先

规则：创建、查看、编辑和完成任务不依赖网络。引入远端数据源时，上层仍从本地持久化事实源读取任务。

理由：网络不是 Android 应用可依赖的稳定前置条件，用户的核心任务数据必须随时可用。

执行：Repository 负责协调数据源；同步失败不阻止读取本地任务；为离线读写和恢复建立测试。

## II. 状态单向流动

规则：UI 渲染不可变状态，事件向下传递，数据变化从事实源重新流回 UI。不得在多个层次维护同一份可变任务数据。

理由：单向数据流让生命周期、并发与测试行为更容易推理。

执行：ViewModel 是屏幕级状态持有者；Composable 不直接做持久化；评审追踪事件到事实源的完整路径。

## III. 用户数据不可用开发便利交换

规则：已发布 Room Schema 的变化必须有显式 Migration 与升级测试，不得使用破坏性迁移回退。

理由：任务是用户创造的数据，静默丢失不可接受。

执行：提交导出 Schema、迁移实现、真实起止版本测试，并验证代表性数据保留。

例外：仅限从未发布且不存在真实用户数据的原型；必须在 Plan 中记录。

## IV. 复杂度必须有需求理由

规则：保持清晰 UI 层和数据层；领域层只在逻辑跨消费者复用或显著降低复杂度时引入。

理由：形式化分层本身会产生代码、维护和导航成本。

执行：Plan 说明新增抽象解决的具体问题；只转发 Repository 的单用途 Use Case 默认不引入。

## V. 可观察行为必须可验证

规则：每条验收标准对应自动化测试或明确人工验证。完成声明必须区分通过、失败、跳过与未运行。

理由：没有证据的完成无法在团队与 CI 中复现。

执行：Plan 建立验收—证据映射；Tasks 写明验证命令；交付摘要列出残余缺口。

## VI. 用户信任采用最小权限

规则：权限、通知、后台执行、遥测、外部工具和密钥只获得完成任务所需的最小范围。

理由：便利不能掩盖隐私、安全和外部副作用。

执行：敏感数据不进入提示、日志和仓库；外部写操作逐次审批；发布与普通 PR 验证隔离。

## 冲突与修订

方案与宪法冲突时，在 Plan 中记录冲突、用户影响、替代方案、临时性和回收条件，并等待负责人决定。修订宪法必须更新版本、理由、受影响规则与迁移动作，不能由单个功能顺手完成。
