# Room、DataStore 与离线数据评审参考

只在改动涉及持久化、Repository、序列化、同步或离线行为时使用。

## 事实源与 Repository

- 确认 UI 和 ViewModel 不直接访问 DAO、DataStore 或网络数据源。
- 离线优先读取应来自本地事实源；网络结果先持久化，再由本地流向上层发布。
- 检查同一实体是否存在多份长期可变缓存并可能分叉。
- 检查模型映射是否丢字段、错误转换时区或改变排序与空值语义。

## Room Schema 与 Migration

一旦 Entity、索引、列、关系、Database version 或 type converter 改变：

- 检查 Schema 版本是否正确递增；
- 检查项目是否导出并提交新 Schema；
- 检查所有受支持起点都存在迁移路径，而非只检查最近版本；
- 禁止以 `fallbackToDestructiveMigration` 代替真实迁移；
- 不允许修改已经发布的历史 Schema 来掩盖差异；
- 升级测试必须插入代表性数据并断言数据保留与新结构可用；
- 同时覆盖全新安装与关键 DAO 读写。

## DAO 与并发

- 检查查询排序是否确定，过滤是否与产品语义一致。
- 检查多表写入是否需要事务，读改写是否存在丢失更新。
- Room 不应在主线程执行阻塞访问；线程切换责任应符合项目约定。
- Flow 查询应在相关表变更后产生新值；一次性查询不要被误当持续事实源。
- 检查删除、级联、唯一索引、冲突策略与外键对真实用户数据的影响。

## DataStore 与序列化

- 无值、旧值、未知枚举和损坏数据要有明确回退。
- key 改名或序列化变化要考虑已有用户，不得静默重置关键偏好。
- 写入失败不能错误地破坏本次会话核心操作；错误处理符合 Spec。
- 不把大型结构化业务数据硬塞进偏好存储来绕过 Room。

## 隐私与可观测性

- 不把任务内容、标识、令牌或数据库路径泄露到不必要日志。
- 诊断日志保留版本、迁移起点和错误类型等排障信息，并按政策脱敏。
- 测试 Fixture 不使用真实用户数据或生产凭据。
