# 20｜协作与审查：从“代码能跑”到“改动可信”

上一讲所有测试都转绿了。现在最危险的一句话是：“既然测试通过，就可以合并。”

测试只能证明它覆盖的行为，不能自动发现错误需求、遗漏场景、不必要复杂度或错误的测试本身。Review 的职责不是再读一遍代码，而是主动寻找让这次改动不可信的证据。

## 先切换角色

实现者知道自己想做什么，容易把代码读成“它应该做什么”。评审者必须从 diff 和合同出发，问“它实际会做什么”。

在 Codex CLI 中，可以使用 `/review` 审查未提交改动、相对某个基线的分支或指定提交。也可以显式调用课程中的 Skill：

```text
使用 $android-code-review 审查当前分支相对 main 的改动。
读取 specs/001-task-filter/spec.md、plan.md 和项目宪法。
只报告会影响正确性、数据安全、生命周期、无障碍或可验证性的具体问题；
不要修改文件。若没有发现，明确说明残余验证缺口。
```

“不要修改”很重要。审查阶段先建立共同事实，再由负责人决定修复。

## Review 的四条证据链

### 从 Spec 到行为

逐条检查验收标准是否真正实现。筛选控件存在，不代表冷启动恢复、两类空状态和完成后即时更新都成立。

### 从事件到事实源

追踪一次点击：UI 是否只发送事件？ViewModel 是否把选择交给偏好 Repository？任务列表是否仍从 Room 派生？如果 Composable 与 ViewModel 各自持有筛选状态，测试也许能通过，但旋转或返回导航时会分叉。

### 从 diff 到回归面

读取完整 diff 和受影响调用者。一个 `TasksUiState` 构造器增加必填字段，可能影响 Preview、测试 Fixture 和其他屏幕；一个 DataStore key 改名可能让旧用户丢失选择。

### 从完成声明到命令

确认哪些命令实际执行，环境是什么。测试报告来自修改后还是旧缓存？仪器测试是否有设备？Lint 是否只跑 app 模块而改动涉及 core 模块？

## Android 特有的审查焦点

### Compose 与状态

检查状态是否被重复持有，Flow 是否生命周期感知地收集，副作用是否使用稳定 key，列表项是否有稳定身份，重组是否会重复触发业务操作。

### 协程

检查 ViewModel 与 Repository 谁负责线程切换，是否使用结构化并发，错误是否被吞掉，测试是否依赖真实延时。

### Room 与数据

本功能原则上不改 Schema。如果 diff 出现 Entity、Database 版本或 destructive migration，这首先是范围越界。查询变化还要检查排序、Flow 更新与空集合语义。

### 无障碍与本地化

用户可见字符串应来自资源；选中状态不能只靠颜色；点击目标、语义角色和大字体布局需要验证。自动测试能覆盖一部分，但不能替代 TalkBack 和视觉检查。

## 如何写一条高质量发现

```text
[P1] 筛选偏好写入失败会回滚当前 UI 选择

UserPreferencesRepository.kt:61 抛出的 IOException 被 ViewModel 外层 combine 终止，
导致 uiState 回到初始 ALL。Spec 要求写入失败时仍保留本次会话选择，
而当前实现会在磁盘失败时立即改变用户正在查看的列表。
建议把会话选择与持久化结果解耦，并为失败路径增加 ViewModel 测试。
```

这条意见有位置、触发条件、违反的合同、用户影响和修复方向。相反，“错误处理可以优化”没有行动价值。

严重程度也要有一致含义：P0 是会阻断发布的灾难问题；P1 是高概率或高影响正确性问题；P2 是应修的常规缺陷；P3 是低风险改进。风格偏好不应冒充高优先级 Bug。

## 没有发现不等于没有风险

一次诚实的“无发现”应该同时说明评审范围：

```text
未发现阻断问题。
已审查：当前分支相对 main 的 8 个文件；已核对 Spec 全部验收；
已运行单元测试与 lintDebug。
未覆盖：真机 TalkBack、大字体视觉检查、冷启动恢复的设备测试。
```

这样，决策者知道剩下的不是“绝对安全”，而是明确的证据缺口。

## 修复发现后必须重审组合结果

不要让 Codex 按评论逐条修完就直接结束。修复可能改变数据流或新增回归。每项修复都要有目标测试，全部完成后再次查看完整 diff，并重新运行受影响的验证矩阵。

评审意见可以过期；修复前先确认当前代码仍存在问题，避免机械应用旧建议。

## 小结

Review 是一次有边界的证伪活动：从 Spec、数据流、diff 和验证四条证据链检查改动。好的发现具体可复现，无发现也要声明审查范围与残余风险。

下一讲，我们把本地证据搬进 CI。重点不是写一份 YAML，而是保证干净环境能够重现相同结论，并正确处理 Android 设备测试与密钥边界。
