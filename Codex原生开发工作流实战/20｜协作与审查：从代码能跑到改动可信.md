# 20｜协作与审查：从“代码能跑”到“改动可信”

测试变绿，只证明已经覆盖的断言成立。它不能自动发现错误需求、遗漏场景、旧缓存、越界修改或错误测试。Review 的工作是主动寻找让这次改动不可信的证据。

这一讲不只给检查表。我们会向 PocketTasks 注入一个真实回归，然后分别用 `/review`、Android Review Skill 和目标测试找出它。

## 先明确审查对象

审查开始前要说清比较范围：

- 未提交工作区；
- 当前分支相对 `main`；
- 指定提交；
- PR 的完整 diff。

在 Codex CLI 中使用 `/review` 选择范围。评审阶段保持只读：先建立事实，再决定是否授权修复。课程还提供 [`$android-code-review`](./配套文件/PocketTasks-codex/.agents/skills/android-code-review/SKILL.md)，它会加载 Compose 或 Room 专项参考，并规定发现格式和停止条件。

## 故障实验：把“进行中”筛选反转

进入一份干净的课程项目或独立 Worktree：

```bash
cd 配套文件/PocketTasks-codex
git status --short
./scripts/lab-patch.sh apply 20-review
git diff -- app/src/main/java/com/example/pockettasks/model/TaskFilter.kt
```

补丁只把 `ACTIVE` 的布尔判断从“未完成”改成“已完成”。现在先不要运行测试，在 Codex 中执行：

```text
/review
```

选择当前未提交改动。一个有效发现应该类似：

```text
[P1] 恢复 ACTIVE 的未完成任务判断

TaskFilter.kt 的变更让 ACTIVE 与 COMPLETED 使用同一个 isCompleted 条件，
导致“进行中”页展示已完成任务。这违反现有 TaskFilterTest 和筛选合同。
恢复取反条件，并运行目标测试覆盖三种筛选。
```

关键不在措辞，而在四项证据：具体位置、触发条件、用户影响、最小修复方向。

## 用确定性测试确认发现

```bash
./gradlew :app:testDebugUnitTest --tests '*TaskFilterTest' --rerun-tasks
```

预期只有 `ACTIVE` 断言失败，`ALL` 与 `COMPLETED` 仍通过。现在你知道：评审发现不是风格偏好，而是可以由现有测试复现的行为回归。`--rerun-tasks` 用来排除培训现场已有编译缓存造成的假绿。

实验结束后先查看 diff，再运行 `./scripts/lab-patch.sh reverse 20-review`。若目标文件已有个人修改，不要机械恢复。完整步骤见 [`docs/labs/20-review/README.md`](./配套文件/PocketTasks-codex/docs/labs/20-review/README.md)。

## `/review` 与 Skill 各自解决什么

`/review` 是 Codex 内置审查入口，适合快速选择工作区、基线分支或提交。Skill 是团队版本控制的评审方法，适合固定 Android 特有检查、严重程度、证据格式和停止条件。

两者可以组合：先用 `/review` 选择范围，再明确调用：

```text
使用 $android-code-review 复核当前分支相对 main 的完整 diff。
读取 specs/001-task-filter/ 和 docs/constitution.md。
不要修改文件；只报告可复现问题和残余验证缺口。
```

不要把两次同模型审查当成完全独立证据。高风险修改还需要另一位开发者、确定性工具、CI 或不同角度的 Subagent。

## 四条证据链

### Spec → 用户行为

逐条核对验收，不把“界面上有三个按钮”误认为“冷启动恢复、完成后更新、空状态和无障碍都成立”。

### 事件 → 单一事实源

追踪实际路径：

```text
Compose 点击 → TaskViewModel → TaskRepository → DataStore
Room Flow → Repository 过滤 → uiState → Compose 语义
```

如果 UI 和 ViewModel 各自保存筛选，短测试可能通过，生命周期切换后仍会分叉。

### Diff → 回归面

读取完整 diff 和调用者。`TaskEntity`、数据库版本、DataStore key、资源名或 `TaskUiState` 构造参数的变化，都可能影响 diff 之外的文件和旧用户状态。

### 完成声明 → 命令证据

确认测试来自修改后的代码；设备是否真实存在；Lint 跑了哪个模块；失败是回归、基线还是环境问题。`assembleDebugAndroidTest` 只证明测试 APK 可编译，不等于测试在设备执行。

## Android 专项审查清单

| 区域 | 要主动证伪的问题 |
|---|---|
| Compose | 状态是否重复、Flow 是否生命周期感知、语义是否完整、副作用 key 是否稳定 |
| 协程 | 是否结构化并发、异常是否吞掉、测试是否依赖真实延时 |
| Room | Schema 与 Migration 是否一致、生产 builder 是否注册、是否破坏性回退 |
| DataStore | 未知值和 IO 异常怎样处理、写失败是否破坏本次会话体验 |
| 无障碍 | 选中态是否只靠颜色、字符串是否资源化、大字体和 TalkBack 是否验证 |
| 构建 | 版本、Manifest、权限、签名和发布配置是否越界 |

## 修复后必须重审完整组合

让 Codex 修复时写清授权边界：

```text
只修复刚才确认的归档任务回归，恢复现有行为，不重构其他代码。
运行 TaskFilterTest；随后展示完整工作区 diff。不要提交或推送。
```

修复完成后再次 `/review`。评论可能已经过期，修复也可能引入新回归。最终结论应区分：

```text
发现：无阻断问题
已审查：工作区相对 HEAD 的 1 个文件
已运行：TaskFilterTest，通过
未覆盖：设备端筛选交互、TalkBack、大字体视觉检查
```

“没有发现”不等于“没有风险”，只代表在声明范围和证据内没有发现可行动缺陷。

## 非交互审查

需要将审查结果交给流水线时，运行：

```bash
./scripts/codex-readonly-review.sh
jq . build/reports/codex/review.json
```

脚本使用只读沙箱与 JSON Schema。它适合生成审查制品，不应直接拥有合并或发布权限。

## 小结

可信 Review 是证伪活动，不是“再看一遍”。课程实验把一行回归连到内置 `/review`、团队 Skill、目标测试和结构化报告，让发现可以复现、修复可以复核、残余风险可以交接。

下一讲会把这些本地证据搬进 CI，并继续保持 API Key、补丁和远端写权限的隔离。
