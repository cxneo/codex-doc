# 11｜事件自动化：用 Hooks 守住关键节点

前面我们要求 Codex 在结束时报告验证、在危险命令前停下来、在长任务中更新状态。问题是：只要一项要求依赖“每次记得”，它迟早就会被忘记。

Hooks 提供了一种事件驱动机制：当会话或工具调用走到特定节点时，运行一段确定性程序。它像门口的闸机，不负责替你设计产品，却能在固定位置检查票据。

## 哪些时刻可以挂 Hook

Codex 支持的生命周期事件包括 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`PostToolUse`、`Stop`、`SessionEnd`，以及上下文压缩和 Subagent 相关事件。

最常见的三种用途是：

- `PreToolUse`：命令执行前识别高风险模式；
- `PostToolUse`：命令执行后收集结果或提醒后续动作；
- `Stop`：Codex 准备结束时检查是否遗漏任务要求。

当前 Hook 处理器使用命令运行。它会通过标准输入接收 JSON，并用退出码和 JSON 输出影响流程。项目中的 Hook 本质上是会自动执行的代码，所以首次加载必须像审查构建脚本一样审查它。

## 一个最小配置

项目级 Hook 可以放在 `.codex/hooks.json`：

```json
{
  "description": "PocketTasks project hooks",
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "python3 .codex/hooks/pre_tool_use.py",
            "statusMessage": "Checking Android command policy",
            "timeout": 5
          }
        ]
      }
    ]
  }
}
```

可以在 Codex 中使用 `/hooks` 查看配置与信任状态。不要因为文件位于仓库就自动相信；分支切换或拉取更新也可能改变将被执行的脚本。

## PocketTasks 的第一个 Hook 应该做什么

不要一开始就在每次改 Kotlin 后运行全量 Gradle 构建，那会让反馈变慢并制造噪音。更好的第一项自动化，是拦截高风险 Android 命令并给出清楚原因。

例如 `PreToolUse` 脚本可以识别：

- `adb shell pm clear`：可能清除真实设备数据；
- `gradlew publish` 或上传任务：可能改变外部制品；
- 包含签名文件、服务账号或 `local.properties` 的读取；
- 无目标限制的设备卸载或数据操作。

能用 Rules 表达的固定命令前缀，优先用 Rules；需要检查包名、路径或当前分支等上下文时，再用 Hook。两者是互补关系。

## Stop Hook：完成前检查证据

PocketTasks 可以设计一个轻量 Stop Hook，读取当前任务状态，提醒 Codex：

- `tasks.md` 是否仍有被宣称完成但未勾选的项；
- 工作区有 Kotlin 或 Gradle 改动时，是否记录过验证命令；
- 是否存在未说明的失败或未运行测试。

但不要让 Hook 凭空判断“代码一定正确”。它只能检查证据是否存在，不能替代代码评审与测试含义。

## Hook 的输入输出契约比脚本语言更重要

Hook 收到的是结构化事件。脚本应只读取需要字段，对缺失字段有安全默认，并把输出限制在明确协议内。失败策略也要提前决定：

```text
安全策略检查失败 → 倾向阻断并说明人工处理方式
辅助日志收集失败 → 记录警告，不应让开发完全停摆
格式化建议失败   → 不应误报为产品代码失败
```

还要设置合理超时。一个在每次命令前执行 30 秒的 Hook，会迅速被团队绕过；快速、确定、低噪音才有长期生命力。

## 不要在 Hook 里埋秘密副作用

下面这些做法很危险：自动提交、自动推送、自动上传日志、自动修改失败测试、把整个提示词发送到外部服务。即使出发点是提高效率，它们也改变了权限与数据边界。

Hook 的行为应该在文件名、说明和代码里都容易看懂。外部网络、凭据或状态写入必须显式披露，并接受团队安全审查。

## 本讲实践：先记录，再阻断

实现 Hook 最稳妥的路径是两阶段：

第一阶段只记录匹配事件和将要采取的判断，不改变执行。观察一周，确认没有误判常规 Gradle 命令。

第二阶段只把确认过的高风险模式改为阻断或审批。为每条策略准备允许、拒绝和边界输入的测试样例。

这和写业务功能一样：先建立可观察性，再增加控制。

## 小结

Hooks 把“关键时刻应该做什么”从记忆变成事件机制。适合它的是快速、确定、可解释的检查；复杂语义仍应交给测试、Review 或人的判断。

下一讲，Codex 将不再只接触本地仓库。我们会用 MCP 与 Plugins 连接 Issue、设计和文档等外部系统，同时重新审视数据与权限边界。

2. 哪些策略用 Rules 已足够，哪些确实需要 Hook 的上下文判断？
