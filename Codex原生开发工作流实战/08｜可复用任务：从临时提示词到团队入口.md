# 08｜任务控制台：用命令管理会话、计划和长任务

很多教程把斜杠命令写成一张速查表，读者记住几十个名字，却不知道什么时候该切换会话、什么时候该压缩上下文、什么时候应该从 Plan 进入 Goal。

这一讲不要求死记命令。我们围绕一个 Android 任务，建立一套稳定的会话操作节奏。

> 本章所列命令以 Codex CLI 当前文档为基准。不同入口和版本可能只暴露其中一部分；输入 `/` 查看当前客户端实际可用的命令。

## 先分清三种入口

| 类型 | 例子 | 谁提供 | 适合解决什么 |
|---|---|---|---|
| Codex 内置命令 | `/plan`、`/goal`、`/diff` | Codex 客户端 | 控制会话和产品状态 |
| Skill | `$android-code-review` | 个人或仓库 | 复用一套团队方法 |
| 普通模板 | `specs/000-template/spec.md` | 项目文件 | 固化文档结构和交付合同 |

不要把一段 Prompt 模板叫成“自定义斜杠命令”。如果流程需要脚本、参考资料和明确触发策略，应升级为 Skill；如果只是文档骨架，就老老实实放在仓库中。

## 一张按意图组织的命令地图

### 看清当前边界

| 命令 | 用途 | 使用时机 |
|---|---|---|
| `/status` | 查看模型、权限、可写根目录和上下文 | 会话开始、切换策略后 |
| `/permissions` | 调整当前权限模式 | 任务从调查进入修改前 |
| `/debug-config` | 查看配置层和组织约束 | 行为与配置预期不一致时 |
| `/usage` | 查看账户用量 | 长任务或培训排障时 |

### 提供上下文

| 命令 | 用途 |
|---|---|
| `/mention` | 把文件或目录明确附加到下一条请求 |
| `/ide` | 在支持的 IDE 扩展中带入打开文件和选区 |
| `/memories` | 控制当前聊天是否读取或生成本地记忆 |
| `/mcp` | 查看当前可用 MCP 工具；`/mcp verbose` 显示详情 |

### 控制任务

| 命令 | 用途 |
|---|---|
| `/plan` | 先调查和形成实施计划 |
| `/goal` | 为长任务设置持续目标，支持 `edit/pause/resume/clear` |
| `/ps` | 查看当前聊天启动的后台终端 |
| `/stop` | 停止当前聊天的后台终端 |
| `/side` 或 `/btw` | 临时问一个旁支问题，不打断主聊天 |

### 管理会话

| 命令 | 用途 |
|---|---|
| `/compact` | 总结当前聊天，释放上下文空间 |
| `/fork` | 从当前聊天分叉另一种方案 |
| `/resume` | 恢复保存的聊天 |
| `/new` | 在同一 CLI 中开始全新聊天 |
| `/rename` | 为聊天设置可识别名称 |
| `/archive` | 归档当前聊天并退出 |
| `/delete` | 永久删除聊天和后代会话，谨慎使用 |

### 检查交付物

| 命令 | 用途 |
|---|---|
| `/diff` | 查看当前工作树改动，包括未跟踪文件 |
| `/review` | 对工作树发起审查 |
| `/copy` | 复制最近一次完成回复 |
| `/skills` | 浏览并调用当前可用 Skill |
| `/hooks` | 查看、信任或禁用 Hooks |

## 从五分钟问题到半天任务

同一个“增加任务筛选”需求，在不同阶段需要不同控制方式。

### 阶段一：先确认现场

进入配套项目：

```bash
cd 配套文件/PocketTasks-codex
codex
```

先输入：

```text
/status
```

检查项目根目录、权限和上下文，再输入：

```text
/plan 调查任务筛选的当前实现。先读取 specs/001-task-filter/spec.md、
AGENTS.md 和相关源码，不修改文件。输出事实、缺口、实施顺序和验证命令。
```

预期：Codex 处于计划模式，先调查已有实现，而不是马上生成一套平行架构。

### 阶段二：把计划变成持续目标

计划经人工确认后输入：

```text
/goal 按 specs/001-task-filter/plan.md 和 tasks.md 完成任务筛选；
每个任务先测试后实现，保持 :app:testDebugUnitTest 通过，
未经明确授权不修改数据库 schema。
```

Goal 最长 4,000 字符。详细合同应保存在文件里，Goal 只保存目标、边界和完成标准。

随时输入 `/goal` 查看目标；需要临时暂停时：

```text
/goal pause
```

目标不会扩大权限。即使 Goal 写了“完成发布”，Codex 仍不能绕过沙箱、审批或仓库边界。

### 阶段三：后台命令与旁支问题

Gradle 运行时间较长时：

```text
/ps
```

确认正在执行的命令和最近输出。不要因为终端暂时安静就重复启动第二个构建。

如果你想问“为什么这里不用 Use Case”，但不想让主任务偏航：

```text
/side 解释当前架构为什么没有新增 Use Case；不要修改主任务计划。
```

### 阶段四：上下文变长以后

任务跨越多轮调查、实现和测试后，先让 Codex 写一个状态块到任务文件或聊天，再输入：

```text
/compact
```

压缩前应确保这些信息已有可靠落点：

- 已完成和未完成任务；
- 当前失败测试；
- 已确认决策和被拒绝方案；
- 实际修改文件；
- 下一条验证命令。

不要把 `/compact` 当成项目记忆。长期事实仍然要写入 Spec、Tasks、ADR、AGENTS 或测试。

### 阶段五：审查与收尾

```text
/diff
/review
```

先看改动半径，再切换成审查角色。审查完成后运行项目验证，而不是只接受文字结论：

```bash
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
```

## 什么时候使用 `/fork`

以下情况适合分叉聊天：

- 想比较 DataStore 与 SavedStateHandle 两种持久化方案；
- 主任务已经有稳定证据链，但要探索一个高风险替代方案；
- 希望保留原计划，避免新假设污染主聊天。

分叉的是聊天上下文，不会自动隔离同一工作目录中的文件修改。需要代码隔离时，配合独立 Git 分支或桌面 Worktree。

## `/resume` 不等于环境一定还在

恢复聊天可以找回上下文，但外部环境可能已经变化：

- 分支被其他人更新；
- Gradle daemon 或模拟器已经停止；
- 工作目录存在新的未提交改动；
- API、依赖或外部 issue 状态发生变化。

恢复后先执行：

```bash
git status --short
git branch --show-current
./gradlew :app:testDebugUnitTest
```

然后请 Codex 对照 Goal 和任务文件重新确认状态。

## 把稳定流程升级成 Skill

当一个任务具备以下特征时，才值得封装成 Skill：

- 会在多个项目或 PR 中重复；
- 输入、步骤、产物和停止条件可以说清；
- 有参考资料或脚本可以渐进加载；
- 能通过正向和反向案例验证质量。

例如 Android 代码审查适合成为 Skill；“帮我看看代码”不适合，因为它没有明确的审查范围、发现格式和验证合同。

## 本讲练习

在一个无风险练习分支完成以下过程：

1. `/rename pockettasks-filter-training`；
2. `/status` 检查边界；
3. `/plan` 调查筛选功能；
4. 确认计划后设置 `/goal`；
5. 用 `/side` 询问一个不改变计划的问题；
6. `/diff` 和 `/review`；
7. 运行 Gradle 验证并归档聊天。

## 完成标志

你不需要记住全部命令，但应该形成以下节奏：

```text
看清边界 → Plan 调查 → 人工确认 → Goal 实施
→ 监控后台命令 → Diff → Review → 独立验证 → 归档
```
