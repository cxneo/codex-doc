# 16｜顶层设计：搭建 Android 项目驾驶舱

前 15 讲像是在桌上认识零件：AGENTS.md、宪法、Rules、Hooks、MCP、Skills、Subagents 和非交互执行。现在我们要把它们装进同一辆车。

所谓“项目驾驶舱”，不是一个巨大的配置目录，而是一套让需求进入后知道往哪里走、风险出现时知道在哪里减速、完成时知道看哪些仪表的协作系统。

## 从驾驶问题反推部件

先不要问“Codex 有哪些功能”，而问团队每天遇到什么问题：

```text
它不知道项目从哪里读      → AGENTS.md
它不理解我们为何这样设计  → constitution.md
需求每次写法不同          → Spec / Plan / Tasks 模板
危险命令靠人工记忆        → Sandbox / Approval / Rules / Hooks
Android 评审经验难复用     → Skill
跨层调查太慢              → 只读 Subagents
完成声明缺少证据          → 验证矩阵 + Review + CI
```

只有能解决真实问题的部件才进入驾驶舱。否则它只会增加维护成本。

## PocketTasks 的目录设计

课程配套文件使用下面的结构：

```text
PocketTasks-codex/
├── AGENTS.md
├── docs/
│   └── constitution.md
├── .codex/
│   ├── config.toml
│   ├── hooks.json
│   ├── hooks/
│   │   └── pre_tool_use.py
│   ├── rules/
│   │   └── default.rules
│   └── agents/
│       ├── android-explorer.toml
│       └── android-reviewer.toml
├── .agents/
│   └── skills/
│       └── android-code-review/
└── specs/
    ├── 000-template/
    │   ├── spec.md
    │   ├── plan.md
    │   └── tasks.md
    └── 001-task-filter/
        ├── spec.md
        ├── plan.md
        └── tasks.md
```

这个结构刻意把“知识”“能力”“安全”和“任务”分开。一个文件只有一种主要职责，读者才能知道改规则时会影响什么。

## 一项需求在驾驶舱中怎样流动

以“增加任务筛选”为例：

```text
产品想法
  ↓ 读取 AGENTS 与宪法，先调查现状
spec.md：行为、范围、验收、问题
  ↓ 人确认
plan.md：状态所有权、DataStore、ViewModel、测试策略
  ↓ 人确认高风险决定
tasks.md：按依赖排序的小步工作
  ↓ Codex 实现，Rules/Hooks 约束命令
目标测试 → 单元测试 → Lint → 构建 → 设备测试
  ↓ android-code-review Skill 独立审查
人工评审 / CI / 合并
```

AGENTS.md 不是每一步都重复抄写，但它始终在背景中生效；宪法只在需要做取舍时发挥作用；Hooks 只在事件触发时运行；Skill 只在相应任务出现时加载。这就是渐进式工作流，而不是“每次启动全套仪式”。

## 驾驶舱的三个设计原则

### 原则一：默认路径必须短

新同事进入仓库，读根 AGENTS.md 就应知道入口和验证命令。不要要求先读十份文档才能修一个文案。

### 原则二：风险越高，流程越深

可以建立三条车道：

| 车道 | 示例 | 最小流程 |
|---|---|---|
| 快速 | 文案、测试命名、小样式 | 目标 + diff + 最窄验证 |
| 标准 | 新交互、跨 UI 与数据层 | Spec + Plan + Tasks + Review |
| 高风险 | Room 迁移、权限、发布、同步 | 标准流程 + 专项 Skill + 人工审批 + 完整证据 |

流程深度由失败代价决定，不由代码行数决定。

### 原则三：每个规则都有唯一权威位置

命令入口在 AGENTS.md；长期理由在宪法；任务行为在 Spec；技术决定在 Plan；执行状态在 Tasks；可自动判断的政策在 Rules 或 Hooks。其他地方只链接，不复制。

## 配置为何不能盲目复制

课程中的 `config.toml` 采用保守权限，示例 Rules 阻止清设备数据，Hook 检查危险命令。这些选择适合教学，但你的仓库可能有不同模块名、CI 环境和设备策略。

复制后必须逐项回答：文件路径是否真实、命令能否运行、Hook 是否可信、规则会不会误伤、团队是否使用对应服务。项目级 `.codex` 只有在受信任仓库中才应启用。

## 从最小驾驶舱开始落地

不要在第一天引入所有部件。推荐四周渐进路线：

第一周：根 AGENTS.md、项目宪法、三条已验证的 Gradle 命令。

第二周：Spec / Plan / Tasks 模板，在一个中等功能上完整跑通。

第三周：根据真实风险增加 Rules 和一个轻量 Hook。

第四周：把重复成功的 Android 评审提炼为 Skill，再考虑 Subagents 与 CI。

每周复盘三个指标：遗漏是否减少、评审是否更容易、流程成本是否合理。没有产生价值的配置应删减。

## 驾驶舱的完成定义

不是目录全部存在，而是一个不参与搭建的同事能够：

1. 在十分钟内理解项目入口和验证方式；
2. 把一个模糊需求写成可评审 Spec；
3. 让 Codex 在约束内完成小步修改；
4. 区分实际通过、未运行与失败的验证；
5. 在危险动作前得到明确阻断或审批；
6. 从提交追溯到需求、计划与测试证据。

这六点可以作为团队验收驾驶舱的真实测试。

## 小结

项目驾驶舱是一套信息与控制的路由系统：长期知识有位置，临时任务有链路，执行能力有边界，完成结果有证据。它应该从小开始，由真实问题推动演进。
