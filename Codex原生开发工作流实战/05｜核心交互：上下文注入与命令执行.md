# 05｜核心交互：上下文注入与命令执行

上一讲完成了一次安全会话。表面上，你输入自然语言，Codex 返回修改；内部真正推动任务前进的，是两个不断交替的动作：获得上下文，以及使用工具验证或改变世界。

理解这两个动作，你就能解释大多数“它为什么没懂”和“它为什么做多了”。

## 上下文不是越多越好

上下文是 Codex 在当前时刻可用的信息，包括你的请求、会话历史、项目指令、打开或提及的文件、它主动搜索的结果、命令输出与工具返回。

把整个 Android 仓库一次性塞进去并不会自动变聪明。`build/`、生成代码、二进制和无关模块会稀释重点。高质量上下文更像一张逐步展开的地图：先给目标和入口，再沿真实依赖追踪。

以 PocketTasks 的“完成任务后列表没有刷新”为例，合理的调查路径是：

```text
PocketTasksScreen
  → 用户事件交给谁
TaskViewModel
  → 写操作调用谁、uiState 从哪里来
TaskRepository
  → 是否观察 Room Flow
TaskDao
  → UPDATE 与查询是否会触发失效通知
相关测试
```

如果只把 `PocketTasksScreen.kt` 贴给 Codex，它可能用局部 `mutableStateOf` 掩盖问题，却绕开项目的事实源。

## 四种上下文，各有职责

第一种是任务上下文：这次为什么改、范围在哪里、成功标准是什么。它通常来自你的请求和 Spec。

第二种是项目上下文：模块结构、架构约定、构建命令、禁止事项。它适合放在 `AGENTS.md` 与项目宪法中。

第三种是现场上下文：相关代码、调用链、历史错误、测试输出。Codex 应通过搜索和命令在任务中获取。

第四种是外部上下文：设计稿、Issue、API 文档、监控数据。它可以通过文件、链接或 MCP 接入，但要控制权限与数据边界。

把短期任务写进永久规则，会让 AGENTS.md 膨胀；把长期架构每次临时口述，则会造成漂移。工程化的第一门手艺，就是把信息放到正确的生命周期里。

## 用文件、IDE 和图片提供精确入口

在 CLI 会话中，使用 `/mention` 明确附加文件或目录，比说“看看那个 ViewModel”更可靠：

```text
/mention app/src/main/java/com/example/pockettasks/ui/TaskViewModel.kt
```

在支持的 IDE 扩展里，`/ide` 可以把打开文件、当前选区和诊断带入下一条请求。它不是读取 Android Studio Compose Preview 的通道；Android Studio 仍通过 CLI、桌面应用或受控 Computer Use 与 Codex 配合。

Android 问题经常包含视觉证据。CLI 可以在启动时附加图片：

```bash
codex -i evidence/list-before.png -i evidence/list-after.png
codex --image evidence/crash-dialog.png
```

给图片配上文字合同：设备、系统版本、复现步骤、预期和实际结果。截图能证明“画面是什么”，不能自动证明状态来源、生命周期或数据库行为。

## Shell 是 Codex 的手和眼睛

仅靠阅读，Codex 只能推测。Shell 让它获得事实：

```bash
rg "class TaskViewModel|class TaskRepository" app/src
./gradlew :app:testDebugUnitTest --tests '*TaskRepositoryTest'
./gradlew :app:lintDebug
git diff --check
git diff -- app/src/main
```

搜索告诉它代码在哪里，测试告诉它行为是否满足，Lint 告诉它平台约束是否被破坏，Git diff 告诉它改动是否越界。

但 Shell 也是风险来源。一条范围清楚的目标测试与一条下载并执行未知脚本的命令，不应获得相同信任。后面的审批、沙箱与 Rules 会把这种差异写成机制。

## 用“证据请求”替代“相信我”

比较两种结束语：

```text
A：已修复刷新问题并添加测试。

B：TaskRepository 组合 Room 与筛选 Flow，TaskViewModel 通过 stateIn 生成 uiState；
新增 TaskRepositoryTest 覆盖筛选变化。
已运行 ./gradlew :app:testDebugUnitTest，BUILD SUCCESSFUL；
未运行 connectedDebugAndroidTest，因为当前没有设备。
```

B 更值得信任，不是因为文字更多，而是每个结论都能回到文件或命令。你可以在任务一开始就要求这种交付格式，减少结束时的追问。

## 上下文压缩之后会发生什么

长任务中，对话可能被压缩。压缩适合保留目标和重要结论，却不该成为唯一的项目记忆。稳定信息要写入仓库，阶段结果要写入 `plan.md` 或 `tasks.md`，已做与未做要及时更新。

CLI 中可以用 `/compact` 主动压缩，用 `/status` 检查会话状态。更重要的是在每个阶段留下文件化的检查点：

```markdown
## 当前状态

- 已确认：筛选状态属于用户偏好，使用 DataStore 保存
- 已完成：TaskFilter 单元测试
- 待完成：ViewModel 接入、Compose 语义测试
- 风险：进程重建场景尚未在设备验证
```

这比依赖“请记住我们刚才说过”可靠得多。

## 会话状态不等于项目状态

Codex 支持 `/resume` 恢复聊天、`/fork` 探索另一方案、`/side` 临时处理旁支问题。但恢复会话以后，分支、依赖、模拟器和外部 Issue 都可能已变化。

恢复后先检查：

```bash
git status --short
git branch --show-current
./gradlew :app:testDebugUnitTest
```

Gradle 在后台运行时，用 `/ps` 查看进程和最近输出；确认命令确实需要终止后再用 `/stop`。不要因为日志暂时安静就重复启动构建。

需要比较两个实现方案时，`/fork` 只隔离聊天上下文，不自动隔离同一个目录的文件。代码方案还需要独立分支或桌面 Worktree。

## 本讲实践：一次只读追踪

在 PocketTasks 或你的项目里，让 Codex 完成下面的调查，不允许改文件：

```text
追踪“用户点击完成任务”从 Compose 事件到 Room 写入、再回到 UI 的完整路径。
输出：
- 关键类型与文件路径；
- 每一跳的数据形态；
- 协程作用域与线程切换；
- 事实源在哪里；
- 现有测试覆盖了哪一段；
- 只能推测而无法确认的事项。
```

然后拿它的路径与代码逐项核对。你会很快发现项目中哪些命名和目录足够自解释，哪些知识需要在下一讲进入 AGENTS.md。

加做一个视觉练习：截取 PocketTasks 的任务列表，把图片和 `PocketTasksScreen.kt` 一起提供给 Codex，让它分别列出“截图直接证明的事实”和“必须从代码或设备验证的推断”。

## 小结

Codex 的核心循环是“获得恰当上下文—调用工具取得事实—根据结果继续行动”。上下文要按生命周期分层，命令要按风险控制，结论要回到证据。

下一讲，我们把每次都会重复说明的项目知识写进 `AGENTS.md`，为 Codex 建立一份不会随着聊天窗口关闭而消失的入职手册。

## 思考题

1. 你的仓库里，哪些目录会制造无效上下文，应该在调查时排除？
2. 团队当前的“完成”声明，有多少可以追溯到实际命令输出？
