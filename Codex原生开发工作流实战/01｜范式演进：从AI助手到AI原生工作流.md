# 01｜范式演进：从 AI 助手到 AI 原生工作流

上一讲留下了一个问题：当 AI 不再只回答问题，而是能够读取仓库、修改文件和执行命令时，开发者的角色变了吗？

答案是：编码仍然重要，但你的工作重心会向更上游和更下游移动。上游要把模糊意图变成明确约束，下游要用证据判断改动是否可信。中间的机械执行，才是最适合交给 Codex 加速的部分。

## 从“副驾驶”到“有边界的执行者”

可以把 AI 编程工具的演进分成四个阶段。

第一阶段是补全。你写出函数开头，工具猜下一行。上下文主要来自当前文件，控制权完全在你手里。

第二阶段是问答。你把报错或代码片段放进聊天窗口，它解释原因并给出建议。它懂得更多，却没有完整工程现场。

第三阶段是 Agent。它可以搜索仓库、阅读关联文件、修改多处代码并运行测试。此时，AI 已经从“提供答案”进入“执行任务”。

第四阶段是工作流。团队不再依赖某一次聪明对话，而是把规范、验证、安全边界和专家方法写进仓库。不同成员用同样的入口，得到结构相近、可评审的结果。

真正的工程化发生在第四阶段。

## Android 项目为什么尤其需要工作流

Android 改动很少只存在于一个函数里。以“给待办增加完成状态”为例，看起来只是一个复选框，实际可能穿过整条链路：

```text
Compose 交互
  ↓ event
ViewModel / UI State
  ↓ 调用
Repository
  ↓ 映射
Room DAO 与 Entity
  ↓ 持久化
数据库 Schema
```

此外还有进程重建、生命周期、协程调度、无障碍语义、不同屏幕尺寸、数据库升级和设备测试。一个只看到当前 Composable 的 AI，容易给出局部正确、系统错误的修改。

所以，高质量请求不是“帮我加个 checkbox”，而是让 Codex 先回答三个问题：

1. 这个状态的事实源在哪里？
2. 事件如何穿过现有架构并回到 UI？
3. 哪些测试能够证明离线、重启和筛选场景没有退化？

这三个问题把写代码变成了做工程。

## 新的分工：人定义正确，AI扩大吞吐

在传统流程里，工程师同时承担发现、设计、实现、验证与表达。Codex 可以显著缩短其中的探索和实现时间，但不能替代业务责任。

人的优势在于价值判断：为什么做、先做什么、哪些行为不能改变、失败代价多大。Codex 的优势在于并行阅读、大量搜索、机械修改、执行命令与快速迭代。

因此，一个更稳健的分工是：

```text
人：目标、边界、取舍、验收、最终责任
Codex：探索、方案、实现、验证、结果摘要
仓库：长期记忆、团队规则、自动化证据
```

注意，最后一行非常关键。如果规范只存在于聊天记录中，下次任务仍要从头开始；如果规范进入仓库，它就能同时服务开发者、Codex、代码评审和 CI。

## 第一次练习：先让 Codex 调查，不让它改

找一个你熟悉的 Android 项目，在项目根目录启动 Codex，给出下面的任务：

```text
先不要修改文件。请调查这个 Android 项目的：
1. 模块结构与主要入口；
2. UI 状态如何产生并流动；
3. 数据持久化方式；
4. 本地单元测试、仪器测试、Lint 和构建命令；
5. 你仍然无法确认的事项。

每个结论请给出文件路径作为证据，最后画出一条从 UI 到数据源的数据流。
```

你要观察的不是它“答对多少”，而是它在哪里猜测、哪里缺少项目说明、哪里无法找到验证命令。这些空白，就是后面 AGENTS.md 与项目宪法需要填补的地方。

## 小结

AI 原生开发不是让 AI 接管责任，而是重新设计责任的传递方式：人把意图写清，Codex 把探索和执行做深，仓库保存长期规则，自动化提供验证证据。

但这里还有一个明显缺口：自然语言需求怎样才能稳定地穿过这条流水线？下一讲，我们会认识整套工作流的发动机——规范驱动开发。
