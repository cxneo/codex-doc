# 开篇词｜当 AI 真正进入你的开发工作流

你好，欢迎来到《Codex 原生开发工作流实战》。

先想象一个 Android 团队很熟悉的下午。

产品经理发来一句话：“待办列表加一个已完成筛选，离线时也要正常。”你把需求粘给 AI。几分钟后，它改了 Compose 页面，又在 ViewModel 里塞了一份列表状态，还顺手给 Room DAO 增加了查询。界面能跑，演示顺利，看起来效率惊人。

直到代码评审开始：UI 和数据库各维护一份状态，返回页面后筛选条件丢失；空列表文案没有区分“没有任务”和“筛选后无结果”；数据库测试没有覆盖升级；CI 又因为没有模拟器而跑不了 UI 测试。

问题不在于 AI 不会写 Kotlin。恰恰相反，它写得太快了。真正缺少的是一套让它在行动前理解项目、在行动中遵守边界、在行动后交出证据的工作流。

这就是本课程要讨论的主题。

## 我们不是来学一组神奇提示词

提示词当然重要，但它只是一段对话。工程化要解决的，是对话结束以后仍然存在的问题：

- 新同事怎样让 Codex 迅速理解项目，而不是重复口头交代？
- “完成”到底意味着能编译，还是包括单元测试、Lint、设备测试和文档？
- 哪些命令可以自动执行，哪些操作必须停下来等人确认？
- 一次优秀的 Android 代码审查，怎样沉淀成整个团队都能调用的能力？
- Claude Code 或 Cursor 中已经投入的规则、命令与技能，怎样迁移而不推倒重来？

如果这些问题没有答案，AI 只是一个能力很强、但每次入职都失忆的临时外包。我们的目标，是把它变成一个知道项目地图、接受团队制度、能提交可验证成果的协作者。

## 贯穿全课的一辆车

学习工程化很像学开车。只认识发动机、刹车和仪表盘的名字，不等于能够安全到达目的地。你需要知道何时看路、何时换挡、哪里必须减速，以及发生偏航时怎样回到路线。

Codex 的 CLI、桌面应用、AGENTS.md、Rules、Hooks、MCP、Skills 和 Subagents，就是散落的零件。课程前半段会逐个理解这些零件，后半段会把它们装进同一套“项目驾驶舱”。

我们的车叫 `PocketTasks`：一个使用 Kotlin、Jetpack Compose 和 Room 的离线待办应用。你会看到同一个需求如何经历下面的旅程：

```text
模糊想法
  ↓ 澄清
spec.md
  ↓ 设计与拆分
plan.md + tasks.md
  ↓ 小步实现
测试 → 代码 → 验证证据
  ↓ 独立审查
可交付改动
  ↓ 运行反馈
维护与演进
```

前一讲产生的文件，会成为后一讲的输入。这样你学到的不是 24 个孤立功能，而是一条能够在真实仓库里反复运行的流水线。

## 你和 Codex 各自负责什么

这门课不会宣称“把需求交给 AI，人就可以离开”。优秀的人机协作有清楚的责任边界。

你负责目标、取舍与最终责任。你要解释用户真正遇到的问题，决定数据能否丢失、兼容性做到哪里、什么风险可以接受，并审阅最终证据。

Codex 负责高密度的探索与执行。它可以阅读仓库、追踪数据流、生成备选方案、修改代码、运行 Gradle 任务、解释失败并迭代。

规范和自动化则像双方之间的契约：让人的意图可以执行，让 AI 的结果可以检查。

## 学完以后，你应该得到什么

不是一堆“AI 写的代码”，而是三种更耐久的能力。

第一，面对任何 Android 仓库，你都能为 Codex 建立一条清晰的进入路径：从项目说明，到目录级约束，再到可验证的任务。

第二，你能根据风险选择正确的工作方式。一个文案修正不必启动复杂流程；Room Schema 迁移、权限变更和发布配置则必须有更严谨的计划与验证。

第三，你能把个人经验变成团队资产。好的评审清单、故障排查步骤和发版规范，不再只存在于某位资深工程师脑中，而会变成仓库中的 Skills、规则和文档。

如果你已经准备好，我们从第一个问题开始：当 AI 从“给建议”走向“直接改工程”，开发者的角色究竟发生了什么变化？
