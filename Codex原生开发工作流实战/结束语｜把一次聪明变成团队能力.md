# 结束语｜把一次聪明变成团队能力

走到这里，我们从一句“帮我加个任务筛选”出发，走完了 PocketTasks 的需求、设计、实现、测试、审查、交付与维护，也把 Claude Code 和 Cursor 的既有资产映射到了 Codex。如果还没有独立完成一次闭环，先去做[结课实践](结课实践.md)：课程真正结束的标志不是读到最后一页，而是你能提交一条别人可以复现的证据链。

回头看，真正改变开发方式的并不是某一条命令。

是我们在编码前多问了几个会改变行为的问题；把长期约定从聊天写进 AGENTS.md 与项目宪法；用 Sandbox、Rules 和 Hooks 把安全从提醒变成机制；让测试与命令成为完成证据；再把反复成功的方法提炼成 Skills，让一次个人经验可以被团队复用。

## 不要追求一夜之间“AI 原生”

成熟工作流不是设计出来后一次落地，而是从真实摩擦中长出来。

```text
发现一次重复解释
  → 判断它属于项目知识还是任务流程
  → 放入正确文件
  → 在下一次真实任务中验证
  → 有效则保留，无效则删改
```

如果团队现在只有一份经过验证的 AGENTS.md 和三条可靠 Gradle 命令，这已经比拥有二十个无人维护的 Skills 更接近工程化。

## 每月做一次驾驶舱体检

挑一小时，和团队一起检查：

- AGENTS.md 中的路径和命令是否仍然真实；
- 宪法是否仍代表团队愿意执行的原则；
- Spec 模板是否减少了需求歧义；
- Rules 和 Hooks 有没有误报、绕过或失效；
- Skills 是否在真实任务中触发并产生价值；
- CI 报告是否准确区分通过、失败、跳过和未配置；
- 哪些旧配置已经可以删除。

把删除视为同样重要的维护动作。每一条过期规则都会消耗新同事和 Codex 的注意力。

## 衡量结果，不衡量热闹

“每天调用多少次 AI”不是理想指标。更值得观察的是：从需求到首个可评审 Plan 的时间、评审发现的需求遗漏、因范围膨胀产生的返工、验证证据完整度、线上回归率，以及新同事理解项目所需时间。

如果 Codex 让代码生成更快，却让评审和返工更慢，工作流仍需调整。工具速度只有进入完整交付周期，才会变成团队速度。

## 人始终在驾驶座上

Codex 可以读更多文件、运行更多命令、同时探索多个方向，但产品目标、风险接受和最终责任仍属于人。最好的协作不是人退场，而是人把注意力集中到最需要判断的地方。

当你下一次打开一个 Android 仓库，不妨从一个很小的动作开始：让 Codex只读调查项目，并记录它无法确认的三件事。那三处空白，就是你的项目驾驶舱下一步应该照亮的地方。

愿你和团队得到的不只是一次令人惊讶的生成结果，而是一套越来越可信、越来越从容的开发方式。
