# 22｜维护与重构：在证据链上做外科手术

线上反馈“升级后应用打不开”时，最危险的动作是让 Codex 大范围修改迁移代码，直到构建变绿。Room 数据事故需要先还原升级路径，再做最小切口。

PocketTasks 自带一条真实 v1→v2 迁移：给 `tasks` 增加 `archived`，默认值为 `0`。这一讲用可应用补丁模拟“迁移类存在，但生产数据库忘记注册”。

## 先认识四份独立证据

| 证据 | 课程文件 | 能证明什么 |
|---|---|---|
| v1 Schema | `app/schemas/.../1.json` | 老版本真实结构 |
| v2 Schema | `app/schemas/.../2.json` | 当前目标结构 |
| Migration SQL | `PocketTasksDatabase.MIGRATION_1_2` | 如何从旧结构变更 |
| 升级测试 | `DatabaseMigrationTest` | SQL 能保留数据并得到默认值 |
| 生产注册 | `PocketTasksApplication` | 应用真正打开数据库时会使用迁移 |

前四项全对，最后一项仍可能漏。构建成功也不会证明真实旧数据库能打开。

## 故障注入

在干净 Worktree 中：

```bash
cd 配套文件/PocketTasks-codex
./scripts/lab-patch.sh apply 22-migration
git diff -- app/src/main/java/com/example/pockettasks/PocketTasksApplication.kt
./gradlew :app:assembleDebug
```

预期构建仍然成功。补丁只是从生产 `Room.databaseBuilder` 删除：

```kotlin
.addMigrations(PocketTasksDatabase.MIGRATION_1_2)
```

如果设备上已经存在 v1 数据库，v2 应用首次打开时将找不到迁移路径并失败。绝不能用 `fallbackToDestructiveMigration` “解决”，因为那会把用户数据删除后重建。

## 第一轮只读调查

```text
调查当前工作区的 Room v1→v2 升级风险，不修改文件。
读取导出 Schema、Database 版本、Migration、MigrationTest 和所有生产
Room.databaseBuilder 调用。输出：确认事实、假设、真实受影响路径、已有证据、
证据缺口。特别区分“迁移 SQL 存在”和“生产 builder 已注册”。
```

有效结论应指出：Migration 类和测试仍在；生产注册被删除；`assembleDebug` 通过不能覆盖升级行为；现有测试在测试代码中显式 `.addMigrations(...)`，因此不会发现生产 builder 漏注册。

这是本实验最重要的审查技巧：测试可能证明局部组件正确，却没有证明生产接线正确。

## 用日志作为补充上下文

真实事故通常先收到 Logcat 或 CI 日志。脱敏后可以这样分析：

```bash
adb logcat -d -t 500 2>&1 \
  | codex exec --sandbox read-only \
      "只读分析 PocketTasks Room 打开失败；引用关键异常，区分事实与假设，不修改文件"
```

提示词作为参数，日志通过 stdin 作为上下文。不要直接上传真实用户数据、Token 或生产标识；先截取最小相关窗口并脱敏。

如果整份诊断提示词由脚本生成，使用 `codex exec -`。需要流水线消费时使用 `--json` 或 `--output-schema`，不要用自由文本猜字段。

## 修复必须先定义不可破坏项

```text
只修复已经证实的 v1→v2 生产迁移注册缺失。
不得清库、不得修改历史 Schema、不得加入 destructive fallback、不得重构无关代码。
恢复生产 builder 注册后，运行 MigrationTest、JVM 测试、Lint 和 Debug 构建。
设备升级测试若环境不可用，明确标成未运行。
```

最小修复就是恢复 `.addMigrations(MIGRATION_1_2)`。不要重新发明一条重复 SQL，也不要改 v1 Schema 让当前测试看起来一致；用户设备上的历史数据库不会随 Git 被改写。

## 验证矩阵

课程项目当前能提供：

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:lintDebug :app:assembleDebug
adb devices
./gradlew :app:connectedDebugAndroidTest
```

`DatabaseMigrationTest` 使用 v1 Schema 创建数据库，插入“保留我”，以当前 v2 打开，再断言标题仍在且 `archived == 0`。设备必须显示为 `device`，才能声称迁移测试已经执行。

生产级项目还应补：全新安装、每个受支持历史版本到当前版本、包含边界数据的升级、升级后关键 DAO 读写，以及发布渠道的真实配置检查。

## 修 Bug 与重构拆开

事故中可能顺便发现数据库初始化散落、命名不统一。先提交最小数据安全修复，再为重构建立独立 Spec 和回归基线。AI 能快速移动大量代码，也会扩大审查半径；紧急修复越小，越容易证明。

## 写一份不甩锅的复盘

```markdown
## 影响
哪些版本、升级路径和用户行为受影响。

## 时间线
首次引入、首次发布、首次告警、定位、修复与验证时间。

## 根因
生产 builder 漏注册迁移；为什么现有测试未覆盖生产接线。

## 处置
最小代码修复、发布与恢复方式。

## 证据
Schema、测试命令、设备环境、CI 链接与残余风险。

## 系统改进
AGENTS 规则、Review Skill、生产接线测试和 CI 升级矩阵。
```

“某人忘了注册”不是系统改进。把知识放进 `AGENTS.md`，把审查动作放进 Skill，把可确定路径放进自动测试和 CI。

## 实验收尾

完整说明见 [`docs/labs/22-migration/README.md`](./配套文件/PocketTasks-codex/docs/labs/22-migration/README.md)。先查看 diff，再运行 `./scripts/lab-patch.sh reverse 22-migration`；不要用会覆盖个人修改的宽范围 Git 命令。

## 小结

维护阶段的顺序是：时间线、真实升级路径、局部与生产接线证据、最小修复、扩大验证、系统改进。课程的故障补丁证明了一个关键事实：Migration 测试通过，仍不等于生产注册正确。

最后两讲将处理迁移：如何把 Claude Code 或 Cursor 中已经积累的资产带到 Codex，而不是重新制造一套并存配置。
