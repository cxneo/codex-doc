# 22｜维护与重构：在证据链上做外科手术

PocketTasks 2.3.0 发布后出现一条严重反馈：“升级后任务全部消失。”这是维护阶段最考验纪律的时刻。团队很容易在压力下跳到第一个猜测，或者让 Codex 大范围修改迁移代码“直到测试能过”。

维护更像外科手术：先定位病灶和影响范围，再选择最小切口，术后用原有与新增证据确认没有伤及其他组织。

## 第一步：建立事实时间线

让 Codex 只读调查：

```text
调查“从 2.1.x 升级到 2.3.0 后任务丢失”的报告，不修改文件。
读取版本历史、Room Database 版本、Migration、导出 Schema、发布差异和相关测试。
输出：已确认事实、仍是假设的事项、可能受影响的升级路径，以及每条结论的证据。
```

得到的时间线可能是：

```text
2.1.x：Database version 5
2.2.0：升级到 version 6，新增 due_at；存在 MIGRATION_5_6
2.3.0：升级到 version 7，新增索引；只注册 MIGRATION_6_7
受影响用户：从 2.1.x 跳过 2.2.0，直接升级 2.3.0
```

这里还不能直接断言数据一定被删除。要继续检查构建渠道是否启用了 destructive fallback、Room 实际找路径的方式、用户日志与数据库初始化代码。

## 第二步：构造最小复现

一个可靠复现不是“新装 2.3.0 能打开”，而是重建真实升级路径：

1. 使用 version 5 的导出 Schema 创建数据库；
2. 插入一条可识别任务；
3. 使用当前 AppDatabase 打开并执行 5 → 7 升级；
4. 断言结构正确且原任务仍存在。

Room 的 `MigrationTestHelper` 正是为这类升级测试准备。失败测试要保留原始用户数据，而不是只检查表存在。

此时可能出现两种不同根因：

- `MIGRATION_5_6` 代码存在，但当前 Database 构建器没有注册；
- 生产渠道启用了 `fallbackToDestructiveMigration`，找不到路径时重建数据库。

两者修复方式不同。必须让测试先证明真正路径。

## 第三步：做最小修复

如果确认 5 → 6 与 6 → 7 迁移都正确，只是注册缺失，最小修复是补齐注册并删除破坏性回退，而不是重新写一条可能重复变更的 5 → 7 迁移。

如果某个历史迁移本身错误，则要根据已经发布 Schema 设计修复路径，不能修改历史 Schema 文件来“让测试看起来一致”。真实用户设备不会随着 Git 历史被改写。

在任务指令中明确：

```text
只修复已经由升级测试证明的迁移路径问题。
不得清库、不得修改历史导出 Schema、不得降低 Schema 校验；
保留用户数据是第一验收标准。
修复后运行 5→7、6→7 与全新安装相关测试，再运行全量单元测试和 Lint。
```

## 第四步：扩大回归矩阵

数据库修复的验证矩阵至少包括：

| 路径 | 为什么需要 |
|---|---|
| 5 → 7 | 真实事故路径 |
| 6 → 7 | 最近一个直接升级路径 |
| 5 → 6 | 防止旧 Migration 被修复破坏 |
| 全新安装 7 | 确认当前 Schema 可创建 |
| 有数据升级 | 证明不是只保结构 |
| DAO 关键读写 | 证明升级后功能可用 |

随后再做 `testDebugUnitTest`、Lint、构建和设备上的升级演练。数据库测试通过不代表 Compose 展示一定正确，但它提供了数据安全的核心证据。

## 重构与修 Bug 是两种任务

调查时可能发现数据库初始化散落、Migration 命名不统一。这些确实值得重构，但不要和紧急数据修复绑在同一个不可读 diff 中。

先提交最小、可证明的修复；再建立单独 Spec，说明重构目标是降低哪种未来风险、怎样证明行为不变。AI 擅长批量移动代码，也更容易扩大重构半径，所以独立基线和回归测试尤其重要。

## 把事故转化为系统能力

事故复盘不应只留下“某人漏注册迁移”。问流程为何允许它发生：

- 根 AGENTS.md 是否说明 Room Schema 改动要求？
- 数据库目录是否需要局部 AGENTS.md？
- Android Review Skill 是否检查迁移注册与升级组合？
- CI 是否只做全新安装，没有历史 Schema 矩阵？
- 发布清单是否核对 destructive fallback？

把答案落到对应层：知识进入 AGENTS 或宪法，评审方法进入 Skill，确定性路径进入测试和 CI。这样，一次事故才真正变成组织能力。

## 维护中的另一个原则：保留可观测性

不要为了让错误消失而吞掉异常、关闭 StrictMode、禁用 Lint 或删除失败测试。修复必须让系统更容易被理解，而不是更安静。日志要脱敏，但版本、迁移起点、失败类型等诊断信息应可获得。

## 小结

维护阶段的 Codex 应先做证据调查者，再做最小修复执行者。时间线、真实升级测试、最小 diff 和回归矩阵共同防止“修好了眼前，破坏了历史”。事故后的规则、Skill 与 CI 更新则把个人经验变成系统免疫力。

PocketTasks 的完整生命周期已经走通。课程最后两讲处理团队更现实的起点：你们也许已经使用 Claude Code 或 Cursor，怎样保留已有资产，同时迁移到 Codex 的概念与目录。

## 思考题

1. 你们当前的数据库测试是在验证全新安装，还是验证真实升级？
2. 最近一次线上事故，最终沉淀到了哪个可执行机制，而不只是复盘文档？
