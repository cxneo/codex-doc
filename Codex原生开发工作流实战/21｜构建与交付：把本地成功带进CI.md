# 21｜构建与交付：把本地成功带进 CI

本地测试和 Review 都通过了，但交付系统关心另一个问题：在一台没有你的缓存、没有 Android Studio 当前状态、没有手工准备的干净机器上，这份改动仍然成立吗？

CI 是对“可复现性”的考试。Codex 可以帮助搭建和解释流水线，但发布权限、签名密钥和质量门禁必须由团队明确设计。

## 先定义交付合同

PocketTasks 的 PR 合同可以写成：

```text
必过：testDebugUnitTest、lintDebug、assembleDebug
条件必过：connectedDebugAndroidTest（设备 Job 可用时）
人工检查：TalkBack、大字体与关键视觉状态
产物：Debug APK、测试报告、Lint 报告
禁止：PR Job 访问 Release 签名或自动发布
```

有了合同，YAML 只是实现。没有合同，团队很容易把“Job 是绿色的”误当作“需要的东西都验证了”。

## 一份基础工作流的形状

下面是结构示意，Action 版本与 Java 版本应按团队当前基线维护：

```yaml
name: Android CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: "17"
      - uses: gradle/actions/setup-gradle@v4
      - run: ./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: android-reports
          path: |
            app/build/reports/
            app/build/outputs/apk/debug/
```

课程不把某个版本号写成永久真理。真正的工程约束是：使用 Gradle Wrapper；Java 版本与项目工具链一致；依赖与 Action 经过审查并固定到团队接受的版本；失败时保留足够报告。

## 设备测试要单独设计

`connectedDebugAndroidTest` 需要设备。CI 可以使用模拟器 Runner、Gradle Managed Devices 或云设备平台，但它们的启动时间、稳定性和费用不同。

设备 Job 至少要明确：API Level 与 ABI、动画与语言设置、缓存策略、失败截图或日志、超时、重试是否允许。不要简单地在没有设备时跳过，然后仍把 Job 命名为“all tests”。

对 PocketTasks 的筛选功能，设备测试重点是 Compose 语义、Activity 重建和冷启动恢复。数据库升级场景则需要安装旧版本数据库状态后再运行新版本，不能靠全新安装代替。

## 用 Codex 帮助 CI，但不让它成为唯一裁判

可以在传统检查旁增加只读 Codex Job：读取 diff、Spec 和已有报告，输出结构化风险。推荐先设为非阻断：

```text
确定性检查：编译、测试、Lint → 必过门禁
Codex 审查：跨文件语义与证据缺口 → 先提供建议
人工评审：业务取舍、风险接受、视觉与发布决定 → 最终责任
```

当团队积累了足够误报与漏报数据，再决定哪些 P1 发现可以阻断。AI 评审不应替代确定性测试。

## 缓存不是越多越好

Gradle 缓存可以显著提速，也可能掩盖配置不完整。至少保留一种定期或发布前的干净构建路径。遇到“本地成功、CI 失败”，让 Codex 先比较 JDK、Gradle、SDK、环境变量、任务名与缓存，而不是立即修改业务代码。

## 密钥与发布边界

PR 验证通常不需要 Release 签名。来自 Fork 的代码尤其不能接触高权限 Secrets。发布 Job 应与普通验证分离，通过受保护环境、审批和最小权限获得签名材料。

不要让 Codex 打印环境变量、读取 Keystore、生成长期密钥或把签名配置写入仓库。即便它能完成这些动作，也不代表任务授权包含这些动作。

## 失败时怎样让 Codex 排障

给 Codex 的 CI 诊断任务应是只读的：

```text
分析本次 Android CI 失败，不修改代码。
区分：产品代码回归、测试偶发、环境差异、依赖下载、设备启动和配置错误。
引用具体日志位置与相关仓库文件；给出最小复现命令和候选修复，
但在根因确认前不要实施。
```

先分类再修复，可以避免为了绕过环境问题而削弱测试。

## 交付摘要应该像一张仪表盘

```markdown
## CI 结果
- JVM 单元测试：通过，186 项
- Lint：通过，0 个新增问题
- Debug 构建：通过，APK 已上传
- Compose 设备测试：通过，API 35 模拟器
- 人工 TalkBack / 大字体：待产品验收

## 风险
- 尚未覆盖 API 低版本设备
- Release 签名与发布流程不在本 PR 范围
```

它让合并者看到真实状态，而不是自己翻五个 Job 猜结论。

## 小结

CI 把本地承诺变成干净环境中的可复现证据。先定义交付合同，再组织单元、Lint、构建和设备 Job；Secrets 与发布独立隔离；Codex 作为语义审查和排障助手，而不是唯一裁判。

软件上线后，工作并没有结束。下一讲我们会处理一次用户数据消失事故：怎样让 Codex 从症状、版本和迁移路径建立证据链，再进行可验证的外科手术。
