# 结课实践｜为 PocketTasks 增加本地标题搜索

这是一项 90～120 分钟的独立实践。它不提供标准答案；你的目标是证明自己能够把一个小需求安全地穿过 Spec、Plan、TDD、审查和验证，而不是比谁生成代码更快。

## 任务背景

任务数量增加后，用户希望按标题快速找到本地任务。搜索必须离线可用，不能改变任务数据，也不能破坏现有“全部 / 进行中 / 已完成”筛选。

## 已确认约束

- 搜索范围只包含任务标题；
- 匹配忽略大小写，并忽略输入首尾空白；
- 空查询显示当前筛选下的全部任务；
- 搜索与现有状态筛选同时生效；
- 本次不持久化搜索词，进程重建后可以清空；
- 本次不修改 Room Schema、不增加网络、不引入全文检索库；
- Compose 只渲染不可变 UI State，数据流保持单向；
- 不降低现有测试、Lint 和构建基线。

## 开始方式

在课程仓库外复制项目，或创建独立 Worktree / 分支。先确认没有未提交改动：

```bash
cd 配套文件/PocketTasks-codex
git status --short
./gradlew :app:testDebugUnitTest :app:lintDebug :app:assembleDebug
```

开始 Codex 任务时，先要求它只读调查。建议的第一条请求：

```text
先不要修改文件。调查 PocketTasks 当前任务筛选的数据流，指出搜索状态最适合放在哪里。
每个结论给出文件路径；列出至少两个方案、生命周期差异、测试位置和仍未确认的问题。
```

不要把这段提示当作唯一正确写法。你需要判断它的调查是否有仓库证据。

## 必交产物

在新的 `specs/002-task-search/` 中提交：

```text
spec.md
plan.md
tasks.md
completion.md
```

还要提交实现和测试。`completion.md` 必须包含：

```markdown
## 实现范围
- （填写）

## RED 证据
- 命令：
- 失败原因：

## 已运行且通过
- （填写）

## 已运行但失败
- （填写；没有则写“无”）

## 未运行
- （填写；没有则写“无”）

## 审查发现与处理
- （填写）

## 残余风险
- （填写）
```

## 最低验收行为

你的 Spec 至少覆盖：

1. 空查询与只包含空格的查询；
2. 大小写不同但标题相同；
3. 搜索与 ACTIVE / COMPLETED 筛选组合；
4. 完成当前可见任务后列表立即更新；
5. 无匹配项时与“从未创建任务”不同的界面语义；
6. 清空搜索后恢复当前筛选列表。

若你发现需求仍有歧义，把它写入未决问题，不要让 Codex 静默决定。

## 推荐验证层级

按反馈速度从小到大执行：

```bash
# 你新增的最小单元测试
./gradlew :app:testDebugUnitTest --tests '*TaskSearch*'

# 全部 JVM 测试
./gradlew :app:testDebugUnitTest

# 静态检查和 Debug 包
./gradlew :app:lintDebug :app:assembleDebug

# 编译仪器测试
./gradlew :app:assembleDebugAndroidTest

# 有 device 状态目标时才运行
adb devices
./gradlew :app:connectedDebugAndroidTest
```

测试类名可以不同，但 `completion.md` 中的命令必须与真实代码匹配。如果没有设备，明确写“未运行”，不要删除这一项。

## 审查任务

实现完成后，开启一次只读审查。审查者至少检查：

- 查询状态是否出现两个事实源；
- Flow / StateFlow 组合是否造成无意义的重复订阅；
- 字符串规范化规则是否在测试和实现中一致；
- Compose 输入框是否有可测试语义与合理状态提升；
- 空状态是否能区分“没有任务”和“没有搜索结果”；
- 是否出现超出 Spec 的 Room、依赖或架构修改；
- 完成报告是否把未运行项误写成通过。

每条问题给出严重级别、文件路径、行为影响和最小修复建议。没有问题时也要说明审查范围和没能覆盖的风险。

## 100 分评分表

| 维度 | 分值 | 满分标准 |
|---|---:|---|
| Spec | 15 | 范围、非目标、验收、未知项清楚，行为可以验证 |
| Plan | 15 | 命中真实数据流，说明状态位置、取舍、风险与验证 |
| Tasks | 10 | 按依赖排序，每项有文件范围和停止点 |
| TDD 证据 | 15 | 保存真实 RED，最小实现后 GREEN，没有补写“先失败”叙事 |
| Android 实现 | 15 | 单向数据流、不可变 UI State、搜索与筛选组合正确，无无关架构扩张 |
| 测试设计 | 10 | 覆盖空白、大小写、组合筛选、状态变化与空结果 |
| 审查 | 10 | 以行为风险为主，问题可定位，能区分已证实和推测 |
| 完成报告 | 10 | 命令可复现，清楚区分通过、失败、未运行和残余风险 |

建议等级：

- 90～100：可以作为团队样板，再由同事复核一次；
- 80～89：工作流完整，补齐评分表指出的证据缺口；
- 70～79：能够完成任务，但还不适合把自动化扩大到高风险改动；
- 70 以下：回到 17～20 讲，优先修复 Spec、测试或完成报告。

## 加分挑战（不计入基础 100 分）

任选一项，不要全部堆上：

- 用结构化 Schema 输出审查结果，并验证 JSON；
- 创建独立只读 Subagent 调查 Compose 可访问性，主 Agent 决定是否采纳；
- 为团队写一条搜索功能完成后的 AGENTS.md 新约定，并解释为什么它是长期规则；
- 把同一练习用于 Claude Code 或 Cursor 迁移试点，记录资产映射差异。

## 最后的自检

提交前问自己：如果删除全部聊天记录，只保留仓库里的 Spec、代码、测试和完成报告，另一位同事能否理解为什么这样做，并复现“它确实工作”的证据？如果答案是否定的，课程还没有真正结课。
