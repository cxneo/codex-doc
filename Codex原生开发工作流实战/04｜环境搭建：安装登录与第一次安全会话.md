# 04｜环境搭建：安装、登录与第一次安全会话

这一讲只完成一条最小闭环：确认 Android 基线、安装并登录 Codex、以保守权限调查项目、做一个小改动、用真实命令收尾。不要先复制一大份配置；环境问题越早暴露，后续越容易判断是项目失败还是 Agent 改坏了。

## 1. 先证明 Android 项目自己能跑

进入项目根目录：

```bash
./gradlew --version
./gradlew :app:assembleDebug
./gradlew :app:testDebugUnitTest
```

如果没有 `app` 模块，替换为真实模块名。记录 JDK、Gradle、AGP 和失败命令。一个在 Codex 介入前就失败的测试叫“基线失败”，不能在收尾时写成这次修改导致的回归。

设备端命令需要已连接真机或已启动模拟器：

```bash
adb devices
./gradlew :app:connectedDebugAndroidTest
```

`adb devices` 必须显示状态为 `device` 的目标。只执行 `assembleDebugAndroidTest` 是编译测试 APK，不等于测试已经在设备运行。

课程项目的复现基线见 [配套项目 README](./配套文件/PocketTasks-codex/README.md)。

## 2. 安装并验证 Codex CLI

```bash
npm install --global @openai/codex
codex --version
```

CLI 更新频繁，培训当天先记录版本；团队排查同一问题时不要只说“最新版”。安装方式变化时，以 [Codex CLI 官方文档](https://developers.openai.com/codex/cli/) 为准。

## 3. 登录：个人会话与自动化不是一回事

本地交互优先使用浏览器登录：

```bash
codex login
codex login status
```

无法在当前机器打开浏览器时，可以选择设备码流程：

```bash
codex login --device-auth
```

API Key 登录从 stdin 读取，不把值写在命令历史：

```bash
printenv OPENAI_API_KEY | codex login --with-api-key
```

`codex login status` 能显示当前认证方式，已登录时退出码为 0。不要把 `auth.json`、Token、Key、登录日志或终端截图提交到仓库。

CI 优先使用官方 Codex Action；不要把个人登录目录复制给公共 Runner。第 15、21 讲会展开凭据隔离。

## 4. 先审查项目，再决定是否信任

Codex 只在受信任项目中加载项目 `.codex/` 配置、Hooks 和 Rules。信任不是“以后全部命令自动允许”，而是“允许这些仓库级配置进入活动配置层”。

首次打开一个陌生仓库，先人工查看：

```bash
git status --short
sed -n '1,220p' AGENTS.md
sed -n '1,220p' .codex/config.toml
sed -n '1,260p' .codex/hooks.json
```

路径不存在可以跳过。Hooks 是自动执行代码，还要继续打开它引用的脚本。课程项目已在 README 列出审查入口。

启动 Codex 后可以用：

```text
/status
/debug-config
/hooks
```

`/status` 查看会话状态，`/debug-config` 解释活动配置和来源，`/hooks` 查看 Hook 的加载与信任。遇到“配置写了却不生效”，先查信任与优先级，不要盲目改文件。

## 5. 第一次会话保持只读

在 Android 根目录：

```bash
codex
```

使用 `/permissions` 选择只读或最保守的可用权限，然后发出：

```text
先不要修改任何文件，也不要下载依赖。
识别这个 Android 项目的模块、Application/Activity 入口、UI 技术、状态管理、
数据层、本地测试、仪器测试和构建命令。
每个结论给出文件路径；区分已确认、推断和未知。
最后列出下一条最小验证命令，但不要执行。
```

这段请求限定只读、要求证据、允许未知，并把“调查”和“执行”拆开。

## 6. 读懂权限请求

审批决定谁放行越界动作，沙箱决定动作最多能访问什么。把审批切换为自动审查，不会扩大沙箱；把沙箱开到全盘，风险则完全不同。

Android 构建常见行为：写 `build/`、访问 Gradle 缓存、首次下载依赖。批准前检查：

- 命令与参数；
- 工作目录；
- 文件读写范围；
- 网络目标；
- 真机或模拟器目标；
- 是否改变 Git、远端或发布环境。

例如 `./gradlew :app:testDebugUnitTest` 是常规本地验证；`adb shell pm clear ...` 会清数据；`publishRelease` 和 `git push` 会改变外部状态。不能因为都来自终端就按同一风险处理。

## 7. 做一个最小可控改动

调查完成后，切换到允许工作区写入的权限，选择无业务风险任务：

```text
请核对 README 中的单元测试命令是否对应真实 Gradle task。
若过时，只修改这一处文档；不要格式化其他文件。
完成后运行最窄验证，展示 /diff，并说明未运行项。
```

用 `/diff` 查看改动。代码任务按成本扩大验证：

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:lintDebug
./gradlew :app:assembleDebug
```

不要要求“所有测试”，却不确认设备、SDK、密钥和耗时条件。

## 8. 标准收尾

```text
请按四部分收尾：
1. 修改文件和行为；
2. 设计理由；
3. 实际运行的命令及结果；
4. 未运行验证、环境限制和残余风险。
不要把编译、跳过或未运行写成通过。
```

最终由人检查 diff 和关键日志。完整节奏是：

```text
确认基线 → 审查并信任配置 → 最小权限调查 → 小步改动
→ 真实验证 → 检查 diff → 说明残余风险
```

## 常见故障

### Gradle 首次执行长时间没输出

可能正在下载 Wrapper、AGP 或依赖。先检查现有进程和最近输出，不要重复启动多个构建。国内网络环境应使用组织批准的代理或仓库镜像，不要随手执行来源不明的安装脚本。

### Codex 找不到 `adb` 或错误 JDK

Codex 继承启动它的 Shell 环境。对比：

```bash
command -v adb
java -version
./gradlew --version
```

如果 Android Studio 使用内置 JBR，而终端使用另一 JDK，要先统一或明确差异。桌面应用可通过 Local environment 配置项目初始化，不要把个人绝对路径写进团队 `AGENTS.md`。

### 能直接在 Android Studio 内安装 Codex 扩展吗

当前官方 IDE 扩展面向 VS Code 及兼容编辑器，没有官方 Android Studio / JetBrains 扩展。推荐 **Android Studio + Codex CLI／桌面应用** 共用同一仓库。

在地区、平台与组织策略支持时，Computer Use 可以视觉操作 Android Studio 或模拟器，但它可能影响仓库外系统状态，需要单独授权与监督。结构化的 Gradle、adb 和文件操作通常更稳定。

## 小结

第一次成功不是“生成了很多代码”，而是你能区分项目基线、配置来源、权限范围、实际命令和残余风险。后续所有高级能力都建立在这条可复现闭环上。
