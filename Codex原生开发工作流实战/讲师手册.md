# 讲师手册

这份手册帮助你把 24 讲组织成六次 90 分钟的团队训练。它不是逐字讲稿；讲师的任务是让学员在真实终端里经历“提出假设—获得证据—修正判断”，而不是替他们展示一个永远成功的录屏。

## 培训目标

结课后，学员应能：

- 选择合适的 Codex 使用入口，并说清与 Android Studio 的协作方式；
- 用 AGENTS.md、项目宪法和 Spec 减少隐含假设；
- 用审批、Sandbox、Rules 和 Hooks 管理执行风险；
- 在 Worktree 中按 TDD 完成范围受控的 Android 改动；
- 区分 JVM 测试、构建、AndroidTest 编译和设备测试的证据强度；
- 评审 Codex 产出的代码和完成报告；
- 从 Claude Code 或 Cursor 迁移时按行为映射资产。

## 课前准备

讲师应至少提前一天完成：

```bash
ruby 配套文件/validate-course.rb --android
cd 配套文件/PocketTasks-codex
adb devices
```

确认以下事项：

- 学员可以访问仓库和依赖源；
- JDK 17 与 Android SDK Platform 35 可用；
- 至少讲师机器有一个 API 35 模拟器；
- 故障补丁处于可应用状态；
- 不在演示仓库保存 API Key、签名材料和生产账号；
- 团队知道 Codex 请求可能涉及的代码与数据治理规则。

如果网络或账号不稳定，准备两套备用证据：一份成功的命令日志和一份失败日志。备用材料用于讨论，不要把录制结果冒充当场执行。

## 每次课的固定节奏

| 时间 | 活动 | 讲师要做什么 |
|---|---|---|
| 0～10 分钟 | 场景与风险 | 从一次真实 Android 失误开始，不先讲配置 |
| 10～30 分钟 | 概念与边界 | 画出机制放在代理循环的哪个位置 |
| 30～50 分钟 | 现场演示 | 先预测结果，再执行命令 |
| 50～75 分钟 | 学员练习 | 两人一组：执行者与证据审查者 |
| 75～85 分钟 | 故障注入 | 让学员判断哪条证据能暴露问题 |
| 85～90 分钟 | 退出卡 | 每人提交产物、未知项和下一步 |

## 第一课：从聊天到工程现场

对应开篇、01～05。

### 场景

产品说“给 PocketTasks 增加任务筛选”。展示一句模糊请求，然后让学员列出它跨越的 Compose、ViewModel、Repository、Room、DataStore 和测试边界。

### 演示

1. 在项目根目录启动一次只读调查；
2. 要求每个架构结论附文件路径；
3. 比较没有范围/验证命令的请求和带任务合同的请求；
4. 明确 Android Studio 负责工程编辑、预览与设备工具，Codex CLI/桌面应用负责 Agent 工作流。

### 学员产物

一份最多一页的项目调查：模块、数据流、验证命令、三项未知信息。审查者随机点击两条路径确认事实。

### 复盘问题

- Codex 哪个结论来自仓库，哪个只是合理推测？
- 如果当前目录在子模块，加载到的项目指令是否相同？

## 第二课：把团队约定变成可执行边界

对应 06～11。

### 场景

同一条任务在三位开发者机器上得到不同结果；一次误操作清空了模拟器数据。让学员区分信息问题、决策问题和安全执行问题。

### 演示

1. 从重复解释中提炼 10 行左右的 AGENTS.md；
2. 把“数据迁移不可丢数据”写成带理由、执行和例外的宪法条款；
3. 在独立 Worktree 中检查 `.worktreeinclude`；
4. 测试 Rules：`git push` 应请求审批，`adb shell pm clear` 应被拒绝；
5. 运行 Hook 黑盒测试：

```bash
cd 配套文件/PocketTasks-codex
python3 .codex/hooks/test_pre_tool_use.py
```

### 学员产物

一条 AGENTS.md 约定、一条宪法原则、一条 Rules 判定和一项 Hook 测试结果。每项都要说明为何属于这一层。

### 常见误区

- 把所有 README 内容塞进 AGENTS.md；
- 把“项目信任”理解成所有命令自动安全；
- 只写 Hook 脚本，不测试畸形 JSON、缺失字段和拒绝路径；
- 认为 Worktree 可以消除两人同时修改同一语义的冲突。

## 第三课：连接与复用

对应 12～15。

### 场景

团队想让 Codex 读取工单、执行 Android 审查、并行调查三个模块，还希望在 CI 中无人值守运行。先让学员分别判断 MCP/App、Plugin、Skill、Subagent 和 `codex exec` 的职责。

### 演示

1. 画出外部数据/动作经过 MCP 或 App 进入 Codex 的路径；
2. 检查 `android-code-review` Skill 的触发说明、参考资料和输出格式；
3. 让两个只读 Subagent 分别调查 Compose 与 Room 风险，主 Agent 汇总；
4. 运行只读结构化审查：

```bash
cd 配套文件/PocketTasks-codex
./scripts/codex-readonly-review.sh build/reports/codex/training-review.json
```

### 学员产物

一张扩展能力决策表，至少包含数据来源、权限、触发条件、失败可见性、维护者和退出方案。

### 必须提醒

MCP 连接成功不等于授权设计合理；Subagent 并行不等于允许多个执行者同时编辑同一文件；`codex exec` 的结构化输出不等于审查结论天然正确。

## 第四课：从需求到可执行计划

对应 16～18。

### 场景

用“筛选条件在冷启动后仍保留”引出 `rememberSaveable`、`SavedStateHandle` 与 DataStore 的生命周期差异。

### 演示

1. 阅读 `specs/001-task-filter/spec.md`；
2. 找出行为、非目标、未知项和证据映射；
3. 对照代码检查 `plan.md` 是否命中真实组件；
4. 检查 `tasks.md` 的依赖、停止点和最小验证命令。

### 学员产物

为“按标题搜索本地任务”写一个简版 Spec：至少五条验收标准、两个非目标、一个未决问题和一张测试映射表。暂不写实现。

## 第五课：TDD、审查与 CI

对应 19～21。

### 故障实验一：RED 基线

```bash
cd 配套文件/PocketTasks-codex
./scripts/lab-patch.sh apply 19-tdd
./gradlew :app:testDebugUnitTest --tests '*TaskFilterTest'
```

预期出现两个与筛选规则相关的失败。学员应先保存失败证据，再最小修改，最后扩大验证。练习后恢复补丁。

### 故障实验二：审查回归

```bash
./scripts/lab-patch.sh apply 20-review
./gradlew :app:testDebugUnitTest
```

让审查者只看行为风险和证据，不讨论命名偏好。预期至少一个测试暴露 ACTIVE 筛选谓词错误。

### 学员产物

一份完成报告，严格分为实现、已运行、失败/修复、未运行和残余风险。报告中每条“通过”必须能找到命令或报告。

## 第六课：维护、迁移与结课

对应 22～24 与[结课实践](结课实践.md)。

### 故障实验：迁移未注册

```bash
cd 配套文件/PocketTasks-codex
./scripts/lab-patch.sh apply 22-migration
./gradlew :app:assembleDebug
```

构建仍可能通过，这正是实验重点：编译证据不能证明旧数据库升级安全。学员需要指出必须运行的 Migration 测试以及为什么需要旧版本 Schema。

### 迁移讨论

把 Claude Code 或 Cursor 资产分成长期知识、安全策略、可复用流程、外部连接、并行角色和自动化六类。要求学员按行为重建，不以文件名相似作为迁移成功。

### 结课

两人互评[结课实践](结课实践.md)。低于 70 分不建议将工作流扩展到高风险仓库；先补齐 Spec、数据安全或验证证据。

## 退出卡模板

每次课结束前，学员提交：

```markdown
## 今天留下的产物
- 路径或链接：

## 我能复现的证据
- 命令：
- 结果：

## 仍然不确定
- （填写；没有则写“无”）

## 下一次真实任务中的使用点
- （填写）
```

## 讲师评分原则

- 看行为和证据，不看提示词长度；
- 看学员能否解释边界，不看是否记住全部配置键；
- 对如实报告“未运行”给分，对没有证据的“全部通过”扣分；
- 练习失败但定位正确，通常比偶然成功更有训练价值；
- 所有涉及删除数据、发布、外部写入和密钥的动作都必须在安全环境中演练。

## 培训结束后的维护

指定一名课程维护者，每季度运行验证脚本，并对照[章节审校记录](章节审校记录.md)复查时效项。团队项目版本升级、Codex 配置变化或故障实验失真时，更新[版本与兼容性](版本与兼容性.md)和 [CHANGELOG](CHANGELOG.md)，不要静默改写培训基线。
