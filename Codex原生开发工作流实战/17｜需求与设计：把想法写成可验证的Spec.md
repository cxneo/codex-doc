# 17｜需求与设计：把想法写成可验证的 Spec

驾驶舱已经搭好，现在产品发来第一张“车票”：

> 任务多了不好找，做一个进行中和已完成筛选吧，记住上次选择。

如果直接让 Codex 开始改 Compose 页面，它很可能在最显眼的位置实现按钮，却没有弄清“记住”跨越哪个生命周期、完成任务后当前列表怎样变化、空状态如何区分。这一讲只做一件事：把想法澄清为 Spec，不写产品代码。

## 第一步：先调查已有系统

我们给 Codex 的第一条请求是：

```text
先用 /plan 进入计划模式。读取 AGENTS.md、docs/constitution.md 和
specs/000-template/spec.md。
先不要修改产品代码。

调查 PocketTasks 当前任务列表：
- PocketTasksScreen 如何渲染列表与空状态；
- TaskViewModel 的 uiState 和事件；
- Repository / Room 如何提供任务流；
- 是否已有 DataStore 或 SavedStateHandle；
- 相关单元测试与 Compose 测试。

每个结论给文件路径。然后列出实现“全部 / 进行中 / 已完成筛选并记住选择”
之前必须由产品或工程确认的问题，不要自行回答。
```

`/plan` 让本轮聚焦调查和路线，不是承诺永远不写文件。计划完成后仍要由人批准，再进入实现。若任务跨越多天，可同时用 `/goal` 保存更短的持续目标：

```text
/goal
把任务筛选需求澄清成可验证 Spec；完成条件是行为、非目标、异常和证据映射
均无未决歧义。本阶段不修改 Kotlin、Gradle 或 Room Schema。
```

Goal 保持方向，不替代版本控制中的 Spec，也不会扩大权限。

为什么把调查放在提问之前？因为问题也需要项目上下文。仓库如果已经使用 DataStore，问“能否引入 DataStore”就是浪费；如果已有两个不同空状态，则应该询问如何复用，而不是重新设计。

## 第二步：把“记住”拆开

调查后，Codex 应该提出类似问题：

1. 筛选在应用冷启动后仍恢复，还是只要求旋转屏幕不丢失？
2. 当前为“进行中”时，用户完成一项任务，它应立即从列表消失吗？
3. 筛选后无匹配项，显示普通空列表还是专用提示？
4. 筛选是否影响任务排序？
5. 是否需要埋点、深链或多设备同步？

产品确认：跨冷启动恢复；完成后立即按当前筛选更新；显示专用空状态；不改变排序；本期不做埋点、深链和云同步。

这五个答案已经决定了大量实现边界，却还没有锁死技术方案。

## 第三步：写用户场景，而不是页面清单

Spec 中先写行为：

```markdown
## 用户场景一：聚焦进行中的任务

Given 用户同时有进行中与已完成任务
When 用户选择“进行中”
Then 列表只显示进行中任务
And 原有排序保持不变
And 任何任务数据都未因筛选而修改

## 用户场景二：完成当前筛选中的任务

Given 当前筛选为“进行中”
And 列表中存在任务“准备周报”
When 用户将该任务标记为完成
Then 任务持久化状态变为已完成
And 任务从当前列表中消失
And 切换到“已完成”后可以看到它
```

场景描述的是用户能观察到的结果，不规定一定用 FilterChip、Tab 还是 SegmentedButton。这给 UI 设计保留空间，也让测试先于组件选择。

## 第四步：把 Android 生命周期写进验收

“记住选择”最容易产生错解。我们把它写成：

```markdown
## 用户场景三：恢复筛选

Given 用户选择“已完成”
When Activity 重建
Then 当前筛选仍为“已完成”

When 用户完全结束应用并再次冷启动
Then 当前筛选仍恢复为“已完成”

Given 用户从未选择过筛选
When 首次启动应用
Then 默认显示“全部”
```

这段行为排除了只用 `rememberSaveable` 的方案，因为它不能满足所有冷启动持久化语义。至于使用 DataStore 还是其他项目已有机制，留给 Plan 决定。

## 第五步：明确空状态与无障碍

Compose 界面不仅要“看见三个选项”，还要能被辅助技术理解：

```markdown
## 验收标准

- 筛选控件暴露可识别文本和选中语义；不只用颜色表达状态。
- 筛选后无匹配任务时，显示“当前筛选下没有任务”，并提供返回“全部”的操作。
- 完全没有任何任务时，继续显示已有的首次创建引导。
- 横屏与常用字体缩放下，筛选项不遮挡任务列表主要内容。
```

这并不要求 Spec 穷举所有设备，而是把最容易被“能跑截图”掩盖的质量属性提前显性化。

## 第六步：写清非目标与异常

本期非目标包括：不新增云同步；不改变排序；不新增日期、标签或搜索；不为筛选创建新的 Room 表；不改变任务删除语义。

异常行为也要明确：读取筛选偏好失败时使用“全部”并保持任务可用；保存偏好失败不能阻止用户在本次会话切换筛选，错误按项目现有方式记录。

非目标不是消极清单，而是保护交付焦点。它让 Codex 遇到“顺手优化”时知道何处停止。

## 第七步：建立验收—证据映射

```markdown
| 验收行为 | 主要验证 |
|---|---|
| 三种筛选规则正确 | TaskFilter 单元测试 |
| 完成任务后当前列表更新 | TaskRepository / TaskViewModel 单元测试 |
| 默认值与持久化恢复 | 偏好存储测试 |
| 控件可点击、选中语义和空状态 | Compose UI 测试 |
| 旋转 / 冷启动恢复 | 设备测试或明确人工步骤 |
| 无新增静态问题、可构建 | lintDebug + assembleDebug |
```

这张表是后续 Plan 和 Tasks 的桥。如果一条验收标准没有证据，Spec 仍未完成。

## 怎样评审 Spec

评审时不要讨论类名和文件布局，那属于下一阶段。只检查：用户问题是否清楚；每个行为是否有边界；是否仍有多种相反解释；非目标是否保护范围；验收是否可验证；异常与生命周期是否被考虑。

当未决问题会改变用户行为时，停下来等确认。Codex 可以提出选项和影响，却不应假装替产品做了决定。

## 对照课程里的真实产物

完整结果在 [`specs/001-task-filter/spec.md`](./配套文件/PocketTasks-codex/specs/001-task-filter/spec.md)。阅读时做一次反向检查：

```text
需求原话 → 用户场景 → 验收标准 → 证据类型 → 计划中的实现边界
```

配套项目是教学基线，不代表 Spec 每条行为都已经实现。例如“数据库为空”和“当前筛选无结果”必须是两个可观察状态；如果当前 `PocketTasksScreen` 只显示同一句空提示，这应留在任务清单中，不能因为项目可构建就勾成完成。

## 本讲交付检查

- 只修改 Spec 文档，没有产品代码 diff；
- 所有产品决定都有来源，不由 Codex 默认选择；
- 生命周期、异常、无障碍和非目标已写清；
- 每条验收至少有一种可执行或人工证据；
- `/diff` 中没有无关格式化；
- 若使用 `/goal`，其内容仍与批准后的 Spec 一致。

## 小结

这一讲没有写一行 Kotlin，却排除了多个错误方向。一个好 Spec 把模糊形容词变成用户场景，把 Android 生命周期和质量属性写进验收，把非目标变成边界，再把每条行为连到证据。

下一讲，我们会把这份已经批准的 Spec “编译”为 Plan 和 Tasks：决定筛选状态放在哪里、数据如何流动、文件按什么顺序改变。
